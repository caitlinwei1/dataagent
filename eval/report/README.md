# 报告任务评测（第 8 步）

40 个报告任务：20 个归因分析，20 个周期或专题报告。任务都通过开放接口 `POST /openapi/v1/reports` 提交（接口文档：`docs/api/openapi-reports.json`，运行时访问 `/swagger-ui.html`）。

- 出题：`build_tasks.py` → `tasks.jsonl`
- 运行和打分：`eval/scripts/run_reports.py`

## 每个任务带什么

| 字段 | 含义 |
|---|---|
| `keys` | 关键事实，比如“2026 年 2 月成功退款金额”，标准值在 MySQL 上算好。报告正文里要写出这个数，容差 1%；比率写成百分数也算对 |
| `must_mention` | 只有两道题有：数据集里埋了两个根因，归因报告必须点出来。R05 是“华东区域仓 2026-10-12～18 缺货”，R06 是“极速达 2026 Q3 发往西南的时效差” |
| `n_sql` / `n_charts` | 人工完成这份报告需要写几条 SQL、画几张图，用来估算人工耗时 |
| `sample` | 是否属于额度受限时跑的 8 题样本 |

## 打分项

| 指标 | 怎么判 |
|---|---|
| 状态 | 由接口返回：COMPLETED / DEGRADED / FAILED。DEGRADED 表示有步骤降级：Python 重写 5 次仍失败，或者全部 SQL 都返回 0 行 |
| 图表 | 正文里的 ```echarts 块要是合法 JSON 并且含 `series`，前端才能直接渲染 |
| 证据 | 接口在正文末尾附上实际执行的 SQL 和前 5 行结果。这部分由系统生成，不经过大模型 |
| 关键事实命中 | 只在附录之前的正文里找 |
| 数字溯源 | 正文中每个金额类数字（绝对值 ≥ 100，不含百分数、倍数和年份），都要在证据 SQL 的完整结果中找到出处：单元格、列合计、按另一列分组的小计，或同列两个值的差，容差 0.5%。找不到的列为 `untraced`，需要人工核对。接口返回同名字段 `untracedNumbers`，评测脚本用 Python 重新实现了同一规则 |
| 结论 / 建议 | 正文里有没有结论段和建议段 |
| 人工基线（估算） | 10 分钟理解需求，每条 SQL 8 分钟，每张图 5 分钟，写作 10 分钟；归因题再加 10 分钟写结论。**这是按规则估的，不是实测**，见下文“局限” |

### 失败和错误是怎么来的

**1. SQL 重试超限，3 题（R05 / R06 / R21）。** 三题的过程都是：语义一致性校验连续驳回 → 第 10 次时 `SqlGenerateNode` 报“SQL次数生成超限” → 流程直接结束，不出报告。驳回分两种情况：

- R05、R21 是**计划本身有错，校验按错的计划去卡 SQL**。
  - R05：规划器要求“华东地区通过 dim_region 和 prd_spu 关联”，但 schema 里没有这条路径。SQL 生成器改走了正确的 `wms_inventory → wms_warehouse → dim_region`，校验却以“没按指令关联 prd_spu”为由连续驳回。
  - R21：指令里给的退款时间口径和术语表冲突。
  - 两题在 SQL 层面都没有出路，应该回到规划器重新规划，而不是把 10 次重试耗完。
- R06 的驳回是对的：SQL 按“仓库所在大区”过滤，而问题问的是“收货地址所在大区”。只是 10 次之内没能改对。

修复前，接口对这 3 题只返回一个空的 FAILED。现在 `issues` 里会写明超限的是哪一步，以及语义校验驳回了几次、最后一次的理由。

**2. 报告写的数字和 SQL 结果对不上。这是最严重的问题：SQL 是对的，结论是错的。**

- R07：两条 SQL 都对，2 月 68,227.87，1 月 136,390.30，实际**环比 -50%**。报告却把 2 月写成 136,390.30，1 月写成 135,390.30，得出“微增 +0.74%，整体平稳”。溯源检查标出了 7 个错数字，另 1 个是误报（“360°图”）。
- R01：各大区 GMV 的单位是元，报告统一写成了“万元”，放大了 1 万倍。8 个数字都被标出。
- R40：PV 写成 358,335，实际是 369,414，被标出。UV 写成 93,216，实际是 98,987，这个**漏标**了：碰巧等于某两个值的差。另外 17 个标记分别是：表头写了“万元”的单位换算 8 个，报告自己算的均值 5 个，建议里的假设数字 2 个，年份 1 个，以及 4182.83（来源不明）。
- R32 没有被标出的数字，关键事实也对。

所以“数字溯源”是一个**提示人工核对的信号，不是判错器**。它只能抓到“数字不存在”，抓不到“存在但用错了地方”，比如 R07 里把 1 月的数写到 2 月。

**3. R25 结果全空。** SQL 用 `trd_order_item.created_time` 过滤 2026 年 3 月。这个字段是记录的审计时间，全表都是 2024-10-01，属于数据集里故意留的“审计时间 vs 业务时间”陷阱，正确的做法是关联 `trd_order.paid_at`。结果两条 SQL 都返回 0 行，报告据此写了一大段“2026 年属于未来，没有数据”。读起来像一份完整的报告，实际上不可用。现在这种情况会标记为 DEGRADED。

**4. R01 的 Python 降级。** Python 连续 5 次找不到“华东”列，触发第 6 步的显式降级。报告保留了 SQL 结果，正文注明了降级。

### 已做的修复和重跑

| 修复 | 验证 |
|---|---|
| 接口把失败原因写进 `issues`：SQL 重试超限、语义校验驳回次数和最后理由、可行性评估要求澄清、全部结果为空 | R05 重跑两次，都在可行性评估这一步停下：召回没拿到任何销量事实表，模型要求澄清。修复前 `issues` 为空，修复后写明了原因 |
| 数字溯源 `untracedNumbers` 加进接口 | R07 第二次运行（`results/recheck_v2`）又一次算错：2 月写成 92,227.87，实际是 68,227.87。接口直接标出了这个数 |
| **报告节点拿到系统预先算好的列合计**（`ResultTotals`），提示词要求合计和差值直接引用，不要自己相加 | 结果在 `results/totals_v3*`。**R07**：修复前 2 次运行都算错，修复后关键事实命中，正文写的是“68,227.87 元 → 136,390.30 元，-49.98%”，和标准值一致。**R40**：UV 从错的 93,216 变成正确的 98,987。R40 第一次重跑因 DashScope 网络中断而失败，第二次完成 |

这只是两道题、每题一次的重跑，只能说明方向是对的，不能当成比率。

### 下一步最值得做的修复

1. **语义校验连续驳回同一个计划时，回到规划器重新规划**，而不是把 10 次 SQL 重试耗完。可以复用第 5 步的重新规划通道，上限 3 次。这会直接影响 R05 / R21 这类题。
2. **归因题要按假设去召回。** R05 问的是销量，根因却在库存。规划器应该先列出可能的原因域（缺货、价格、流量、履约），再按域去召回表。
3. `untracedNumbers` 非空时，让报告重写一次。
4. 类目层级、汇总表粒度这类口径问题，和第 7 步是同一类。

## 局限

- **人工基线是估算。** 建议 caitlin 亲手做 2～3 题并计时（比如 R07、R32、R40），用实测值校准公式里的系数。
- 只跑了 8 题，结论只能说明“链路通了、主要失败模式是什么”，不能当作稳定的比率。跑完整的 40 题只需一条命令：`python3 eval/scripts/run_reports.py --run full --all`，支持断点续跑。
- 数字溯源会把单位换算、均值这类合理推算也标出来，有误报；也会因为“碰巧等于某个差值”而漏报。
