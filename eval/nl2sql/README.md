# 问数评测：320 题（本轮实际跑 40 题配对样本）

## 题集

`build_questions.py` 生成 `questions.jsonl`，结构是 80 个题族 × 4 组参数。每题都带标准 SQL，SQL 已在 MySQL 上跑通并核对过结果。

| 维度 | 分布 |
|---|---|
| 任务类型 | 单表 96、多表 96、多轮 64（只给最后一轮打分，前面几轮在同一会话里先问）、多步分析 64（规划、SQL、Python、报告整条链路） |
| 意图 | TopN、聚合、对比、趋势、下钻，各 64 |
| 划分 | dev 192 题（48 个题族，月份为 2026-02/03 及去年同期）；holdout 128 题（32 个题族，月份为 2026-04 及 2025-04/10/11/12）。题族和月份两个维度都不重叠 |
| 口径 | 按 `dataset/metadata/business_terms.yaml`，例如 GMV 含运费、销售额按商品实付分摊、大区按店铺归属 |

## 怎么打分

`eval/scripts/run_nl2sql.py` 负责运行和打分。每道题开一个新会话，threadId 就是 conversationId。每次运行把完整的 SSE 流存进 `traces/<id>.jsonl`，结果记录里包括计划、每次生成的 SQL、守卫拦截、每次错误的分类、最终 SQL 和结果、耗时。

**SQL 执行成功率**：最终有结果集返回。

**执行准确率 EX**：比较结果集，不比较 SQL 文本。
- 列名和列顺序不限，多出来的列不扣分。
- 数值允许 0.5% 的相对误差，比率允许写成百分数。
- 维度标签写法不同（例如 IOS 和 iOS端）时，只要数值列全部对上也算对。严格版 EX 要求标签列也一致，两种都会报告。
- TopN 题只要求实体集合正确；第 N 名有并列时，并列中的任意一个都算对。
- 答案很小（不超过 4 个单元格）时，允许形状不同，例如两行一列和一行两列都算对。

**多步完成率**：报告生成出来，过程中没有报错，也没有 Python 降级。有关键数字的题目还会检查报告里是否写出了这个数（误差 1%）。

### 读数和限制

- **确定的提升在“能执行”这一层**。原版召回给错表以后，大模型会编字段（Unknown column），执行报错后反复重写，10 次都没写对，J02-1、J19-1、M13-1 三道就是这样失败的。S02-4 则是因为没有召回到直播表，可行性评估直接判定“答不了”。v2 在 30 道 SQL 题上全部能执行。
- **准确率的提升小，而且有噪声**：+2 道题。多表关联题提升明显（2→4），多轮题少对 1 道（M04-3：v2 把大区按会员地址来算）。
- **多步题打平**：v2 修好了 P07、P16 两道（原版召回卡在选表上），又失败了 P02、P03、P12 三道。其中 P03 是 SQL 一直想在日汇总表上找 `category_id` 列，连续 10 次都失败；P12 是语义校验没通过；P02 是可行性评估阶段就结束了，没有生成计划。这些都是模型推理层面的问题，换模型或者优化提示词才可能改善。
- **样本量**：40 题，并且用的是 qwen-plus，不是计划中的 qwen3.8-flash。不能当成简历上的正式指标。开通付费后用 `scripts/step7/run_eval.sh {upstream_recall,v1,v2} {dev,holdout}` 就能跑完整的 320 题。
