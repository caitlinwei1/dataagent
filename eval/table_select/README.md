# 选表召回评测（Step 3，180 题）

本目录是 Schema 召回这一步的评测：给一个问题，看系统选出的前 5 张表里有没有答这道题必需的表。

- 题目：`questions.jsonl`，180 题（交易 36、供应链 36、商品 30、营销 30、财务 24、跨域 24），其中 13 题是多轮追问。每题标注了必需的表（gold）和题型标签。
- 两个 agent，同一份 86 张表的库：
  - **full**（agent 5，库 `gbi_ecommerce`）：表和字段注释齐全。
  - **partial**（agent 6，库 `gbi_ecommerce_partial`）：38 张表去掉了注释（标签 `ablate` 的 37 题落在这些表上），用来看"注释不全"时掉多少。
- 指标：
  - **R@5 均值**：每题 |gold ∩ 前5| / |gold| 的平均。
  - **R@5 全中**：前 5 张表包含全部 gold 的题目占比。注意有 3 题 gold 超过 5 张表，永远不可能全中。
  - **R@10**：前 10 张表的均值。
- 向量模型：`qwen3.7-text-embedding`（DashScope）。
- 复跑：`python3 eval/scripts/run_table_select.py --agent 5 --tag full`，出表：`python3 eval/scripts/report_table_select.py`。

## 与目标的差距

能力描述里的目标是 Recall@5 从 82.8% 提升到 93.3%。实测：

| | 目标 | full 实测 | partial 实测 |
|---|---|---|---|
| 原版（未修） | 82.8% | 5.6% | 7.9% |
| 修复后只用向量 | - | 69.8% | 72.6% |
| 全通道 | 93.3% | **86.2%**（差 7.1 点） | **82.0%**（差 11.3 点） |
| 全通道 R@10 | - | 95.0% | 93.7% |

- 原版的 5.6% 不能当"基线 82.8%"用：原版根本不看问题（查询词固定为 "default"、只按数据源过滤、取 10 条），排在前面的表取决于向量库的存储顺序，所以每次重建都会变（第一轮是 2.5%）。更公平的参照是"修复后只用向量"的 69.8%。
- 没有为了凑 93.3% 去调参。剩下的漏召主要是不被问题点名的"桥接/中心表"：全通道 full 漏掉的 77 个 gold 表里，`trd_order` 23 次、`trd_order_item` 10 次、`prd_sku` 9 次、`dim_shop` 6 次。

## embedding 是否必要（no_embedding 对照）

- **注释齐全时**：去掉向量通道几乎不掉（85.7% vs 86.2%，全中率反而 71.1% vs 70.0%）。口径表和关键词已经覆盖了大部分问法。
- **注释缺失时**：去掉向量掉 7.8 点（74.2% vs 82.0%）。`ablate` 题从 66.7% 掉到 34.7%，`single` 从 81.6% 掉到 59.2%。没有注释的表只剩英文表名/字段名，只有向量能把"卖了多少钱"连到 `pay_amount`。
- **代价**：向量通道每题约 1.4 秒（两次接口调用），每个 agent 首次向量化 1,232 个文档约 10 分钟。
- **结论**：真实企业库注释往往不全，所以保留 embedding；关键词 + 口径通道作为不依赖接口的兜底。配置项 `gbi.recall.vector` / `gbi.recall.column` 可以单独关掉。

## 各通道的观察

- **列向量（+column）**：两边都稳定 +4~5 点。
- **关键词 BM25（+keyword）**：full 上 +2 点；**partial 上 -5.3 点**，`ablate` 从 90.5% 掉到 58.1%。没注释的表在 BM25 里几乎没有可匹配的词，RRF 等权融合时，关键词通道把有注释的近邻表顶上来。这是一个真实缺陷，没有在本题集上调权重修它，留到 320 题 holdout 再验证（例如按表的注释覆盖率给关键词通道降权）。
- **口径（+term）**：full +5.6 点，`syn`（同义说法）从 58.3% 到 76.3%。
- **枚举值（+value）**：两边基本持平（-0.6 / +0.2），只对 `enum` 题有用，而这类题向量已经答得不错。
- **关联表（+join）**：full +2.6、partial +3.3，主要补 `join` 和 `syn` 题里没被点名的桥接表。
- **多轮（+multiTurn）**：只影响 13 道多轮题，full 的 `multi` 从 56.9% 到 80.3%。

## 需要说明的事

1. **没有干净的 holdout。** 口径和关联表两个通道是看了这 180 题第一轮的漏召分布之后加的；下面第 3、4 条的修复也是看了结果才做的。所以这里的数字偏乐观。step 4 的 320 题（192 dev / 128 holdout）会单独报 holdout。
2. **向量模型换了。** 原计划用 `qwen3.7-text-embedding-flash`，账号上这个模型一直报 "free tier only"，改用 `qwen3.7-text-embedding`，两个 agent 全部重新向量化。第一轮（flash 模型，部分数据源）的结果留在 `results/step3/prev/` 仅供参考。
3. **关联表通道 v1 有缺陷，已修。** 第一版扩展列表里不含种子表本身，RRF 时邻居表都多拿一票、种子表没有，结果把种子表挤下去：full 上 +join 后从 77.2% 掉到 64.2%。修复后种子表排在扩展列表最前。v1 的结果保存在 `results/step3/join_v1/`。
4. **full 的口径一度只有 264/312 条。** agent 5 早期导入的 48 条口径（含 GMV、实付金额、客单价）被软删除，口径通道在 full 上几乎无效（+term 只 +0.1 点）。已恢复为 312 条并重跑 +term 及之后的配置；旧结果在 `results/step3/glossary_264/`。表格里 full 的 vector / +column / +keyword / original 不读口径，没有重跑。
5. **编码。** MySQL 客户端默认 latin1，第一次导入的中文注释是乱码，向量化的是乱码文本。已在所有 mysql 调用里加 `--default-character-set=utf8mb4` 并重新导入、重新向量化；本表的全部数字都在修复之后。
