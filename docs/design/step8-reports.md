# 第 8 步：报告开放接口与 40 个报告任务

## 1. 解决什么问题

第 7 步回答的是“数对不对”。业务方真正拿走的是一份报告：结论、图表，以及能让人相信这些结论的依据。上游 DataAgent 的报告只能在它自己的聊天页面上通过 SSE 流式查看，存在三个问题：

1. **没法集成。** 别的系统（BI 门户、定时日报、IM 机器人）想要“给一个问题，拿回一份报告”，只能自己去解析 SSE 流里几十种节点消息。
2. **报告不可核验。** 报告正文由大模型写，里面的数字从哪条 SQL 来，读者看不到。
3. **没法衡量。** 没有任务集，也没有人工基线，“比人工快多少”无从回答。

## 2. 怎么做的

**开放接口**（`controller/ReportApiController.java`，springdoc 生成 OpenAPI 3 文档）

- `POST /openapi/v1/reports`：传入 `{agentId, question, threadId?, timeoutSeconds?}`。接口内部跑完整条图：意图 → 召回 → 规划 → SQL → 校验 → 执行 → Python → 报告，关闭人工审核，同步返回一个 `GbiReport`。
- `GET /openapi/v1/reports/{threadId}`：返回报告 JSON；`GET .../markdown` 返回 Markdown 原文。`threadId` 就是 conversationId，可以拿它回到第 7 步的追踪记录。
- 文档：`/v3/api-docs`、`/swagger-ui.html`，导出到 `docs/api/openapi-reports.json`。

**组装**（`service/report/ReportAssembler.java`，纯函数，用真实运行录下的流做测试）

| 字段 | 来源 |
|---|---|
| `plan` | 规划器输出的 JSON |
| `evidence` | 每条**实际执行**的 SQL，加上它的结果：列名、行数、前 5 行 |
| `markdown` | 报告节点写的正文，末尾附上系统渲染的“附录：数据证据”。附录不经过大模型，所以就算正文没引用，任何数字都能追到一条可以重跑的只读 SQL |
| `charts` | 解析正文里的 ```echarts 块，校验是否为合法 JSON 并且含 `series`。大模型常写 JS 函数（`formatter: function…`），前端无法渲染 |
| `status` | COMPLETED / DEGRADED / FAILED |
| `issues` | 为什么降级或失败，见下表 |
| `untracedNumbers` | 正文中在 SQL 结果里找不到出处的金额类数字（`NumberTrace`） |

| 情况 | 状态 | `issues` 里写什么 |
|---|---|---|
| Python 重写 5 次仍失败（第 6 步） | DEGRADED | 降级说明 |
| 全部 SQL 都返回 0 行 | DEGRADED | 报告读起来完整，但没有数据支撑，比如 R25 |
| 语义校验连续驳回，SQL 重试超过 10 次 | FAILED | 超限的是哪一步、驳回了几次、最后一次的理由 |
| 可行性评估判为“需要澄清” | FAILED | 澄清内容 |

**数字溯源**（`NumberTrace`）

找出正文里绝对值 ≥ 100 的数字（跳过百分数、倍数、年份和代码块），“万”会按 10000 换算。逐个去证据结果里找出处：单元格、列合计、按另一列分组的小计，或同列两个值的差，容差 0.5%。找不到就列出来，供人工核对。

**任务集与评测**（`eval/report/`，见其 README）

- 40 个任务：20 个归因，20 个报告。每个任务都有用 MySQL 算好的关键事实。
- 其中两道归因题对应数据集里埋好的根因：R05 是华东区域仓缺货，R06 是极速达发往西南慢。
- 人工基线按规则估算：10 分钟理解需求，每条 SQL 8 分钟，每张图 5 分钟，写作 10 分钟，归因题再加 10 分钟。

## 3. 为什么这么做（备选方案）

| 决策 | 选择 | 备选 | 为什么不选备选 |
|---|---|---|---|
| 接口形态 | 同步 REST + OpenAPI 文档，按 threadId 可查 | 直接暴露 SSE 流 | 调用方要理解几十种节点消息；报告是“一次要一个结果”的场景 |
| | | 异步任务 + 回调 | 更适合 5 分钟以上的长任务，但调用方要实现回调。同步接口加超时，再加按 threadId 查询，已经够用；以后可以在此基础上加异步 |
| 文档怎么写 | springdoc 从代码注解生成 | 手写 YAML | 手写的文档会和代码脱节 |
| 证据怎么给 | 系统把实际执行的 SQL 和结果附在报告后面 | 在提示词里要求大模型引用 SQL | 大模型会漏引、错引；确定性的附录一定在 |
| 数字怎么核对 | 确定性溯源，标出可疑数字 | 让大模型自己检查 | 同一个模型刚写错，再检查一遍的可靠性不高，还要多花 token |
| | | 不让大模型写数字，全部模板化 | 最可靠，但报告会很僵硬。现在折中：合计由系统算好交给模型引用（`ResultTotals`），模型只负责组织和解读 |
| 图表 | 正文内嵌 ECharts option JSON，接口里校验 | 后端渲染成图片 | 图片不能交互，前端也不能换主题；JSON 可以直接交给 ECharts |
| 质量怎么判 | 关键事实命中、根因点名、图表合法、证据、数字溯源，全部是规则 | 让大模型给报告打分 | 不稳定、要额外花 token，而且打分的模型看不出 R07 那种“数抄错了”的问题 |
| 人工基线 | 按 SQL 数和图表数估算，注明是估算 | 找人实测 40 题 | 成本太高。建议实测 2～3 题来校准系数 |

## 4. 量化结果

**只跑了 8 题样本**，原因和第 7 步一样：免费额度用完了，模型用 qwen-plus。逐题明细见 `eval/report/README.md`。

| 指标 | 结果 |
|---|---|
| 完成率 | **3/8**。另有 2 题降级：1 题 Python 降级，1 题结果全空；3 题失败 |
| 完成的报告里，有合法图表 / 有证据附录 / 有结论和建议 | 3/3 / 3/3 / 3/3 |
| 关键事实命中 | 2/3 |
| 埋的根因被点出 | 0/2：两题都在 SQL 阶段失败 |
| 平均耗时 | 系统 **5.0 分钟**，人工估算 **64.3 分钟**，节省约 92%（人工是估算值） |
| 数字溯源 | 完成的 3 份报告共 171 个金额类数字，26 个找不到出处。人工核对后：8 个确实写错，其余是单位换算、报告自己算的均值、建议里的假设数字，或误报 |
| 数字完全正确的报告 | 1/3（R32） |

失败原因（来自日志）：

1. **SQL 重试超限（3 题）。** 其中 2 题是“计划本身不可行，校验却按计划卡 SQL”。R05 的计划要求“通过 prd_spu 关联大区”，这条路径不存在；SQL 走了正确的路径，反而被驳回 10 次。只能回到规划器才能解决。
2. **报告抄错数（R07）。** SQL 是对的，实际 -50%；报告把两个月的数搞混，写成“+0.74%，平稳”。数字溯源标出了这些数。
3. **单位错（R01）。** 元写成万元。
4. **审计时间陷阱（R25）。** 用 `created_time` 过滤，查不到数据，又写出一份“看起来完整”的报告。现在会被标记为 DEGRADED。

**修复：报告节点拿到系统预先算好的列合计。** `ResultTotals` 给每一步的结果附上“共 N 行，各数值列合计 = …”，提示词要求合计和差值直接引用这些值。

- R07 修复前 2 次运行都算错，修复后关键事实命中，正文写的是 -49.98%，和标准值一致。
- R40 的 UV 从错的 93,216 变成正确的 98,987。

这只是两道题的重跑，只能说明方向对。这个修复成本很低：不需要多调一次模型，只是把加法从模型手里拿走。

重跑时还观察到：R05 第二次运行在可行性评估这一步就停了，判为“需要澄清”。原因是召回只拿到了维表，没拿到销量事实表。归因题的问题里不会出现根因所在的业务域（库存、仓储），只靠问题本身去召回是找不到的。

## 5. 面试问答

- **为什么做成同步接口？报告要 5 分钟怎么办？** 调用方一次拿到完整结果最简单。超时可以配置；超时以后照样能按 threadId 查到结果。如果要大规模调用，下一步加异步提交和回调，组装逻辑不用改。
- **怎么保证报告里的数可信？** 分三层：
  - 证据附录：系统附上实际执行的 SQL 和结果，而不是大模型说它用了什么。
  - 数字溯源：找不到出处的数字会被列出来。
  - 状态：全空结果、降级、失败都显式标出，不会把一份空报告当成完成。
  - 溯源能抓到“写了一个不存在的数”，抓不到“写了一个存在但用错地方的数”，后者靠的是把计算从模型手里拿走：合计由系统预先算好（R07 修复前后的对比见第 4 节）。
- **完成率只有 3/8，怎么看？** 这是 8 题的样本，不是稳定的比率。更重要的是它把失败分得很清楚：SQL 阶段卡死、计划和校验互相矛盾、报告抄错数。每一类都有对应的修复方向，接口也会把原因写在 `issues` 里，不会只返回一个空的 FAILED。
- **“节省 92% 时间”可信吗？** 系统耗时是实测的，人工耗时是按规则估的，所以它是一个上限估计，前提还是报告本身正确。8 题里只有 1 份数字完全正确，所以要诚实地说：实际节省需要扣掉人工核对的时间。建议实测 2～3 题来校准。
- **为什么不用大模型给报告打分？** R07 这份报告结构完整、语气专业，大模型打分很可能给高分，但它的核心结论是反的。规则检查（关键事实、数字溯源）恰好能抓到这一类错误。
- **归因题为什么难？** 问题问的是“销量为什么下滑”，根因却在库存表里。召回、规划都是围绕问题里的词展开的，不会主动去查一个问题里没提到的业务域。要解决，需要“假设驱动”：规划器先列出可能的原因域（缺货、价格、流量、履约），再分别去召回和查询。
