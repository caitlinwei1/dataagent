# Step 5：计划审核（HITL）的设计与取舍

> 面向面试复盘：做了什么、为什么这么做、考虑过哪些方案、解决了什么问题、怎么验证。

## 1. 要解决的问题

企业问数里，模型先出"执行计划"：查哪些表、分几步、要不要 Python 分析和报告，然后才执行。计划错了，后面所有的 SQL 和分析都白跑，还可能查出误导性的结论。所以析言 GBI 和 DataAgent 都把"人工审核计划"做成可选环节，要求如下：
- 审核人能**确认**、**修改**或**驳回**计划；
- 审核期间不占用线程，审核人可能隔几分钟甚至几小时才回来；之后按 **threadId** 继续执行；
- 驳回会触发重新规划，但要有**上限**，避免无限循环和成本失控。

## 2. 原版 b297203 的做法和问题

做法：
- `compile(interruptBefore(HUMAN_FEEDBACK_NODE))`：图在审核节点前暂停，状态存在检查点（checkpoint）里。
- 恢复时先 `updateState(threadId, 反馈)`，再 `stream(null, config)` 从断点继续。
- 驳回后回到 `PlannerNode` 重新规划。

实测和读代码发现的问题：

| 问题 | 后果 |
|---|---|
| 不能修改计划，只能确认或驳回 | 审核人想"把第 1 步加个过滤条件"，只能驳回后让模型重写，结果可能改出别的问题 |
| 驳回计数和"计划结构自动修复"共用 `PLAN_REPAIR_COUNT` | 模型自己修了 3 次格式错误，审核人一次驳回都没用就被判超限 |
| 上限在进入节点时检查 | 第 3 次重新规划出的计划刚展示，就被判超限，审核人连确认的机会都没有 |
| **超限时把字符串 `"END"` 交给条件边**（真正的结束节点 id 是 `"__END__"`） | 实测会抛 `GraphRunnerException: cannot find edge mapping`，不是正常结束 |
| 规划器只能看到最后一次驳回意见 | 第 2 次驳回"加上同比"后，第 1 次的"按省份拆分"丢了 |
| 检查点只存在 JVM 内存里（MemorySaver） | 审核期间后端重启，或者请求打到另一个实例，这个 threadId 就再也恢复不了 |

## 3. 怎么做的

1. **修改计划**：恢复请求多一个参数 `editedPlan`，内容是审核人改过的计划 JSON。`HumanFeedbackNode` 用规划器同一个解析器校验：
   - 能解析，就替换 `PLANNER_NODE_OUTPUT` 直接执行，不再经过 LLM。之后 `PlanExecutorNode` 照常做结构校验，所以人改出来的非法计划也会被拦下来。
   - 解析不了，就按"驳回"处理，并把修改内容当作驳回原因交给规划器。
2. **独立的驳回计数** `HUMAN_REPLAN_COUNT`，上限 `gbi.hitl.max-replans=3`，可配置。驳回进来时才检查：第 3 次重新规划出的计划仍能确认或修改，第 4 次驳回才结束本轮，并提示"已达到上限，请调整问题后重新提问"。结束时用正确的 `StateGraph.END`。
3. **保留历次驳回意见** `HUMAN_REJECT_REASONS`：规划器拿到的是编号列表，要求同时满足全部意见。
4. **新问题重置预算**：同一个 threadId 问下一个问题时，驳回次数、反馈和修复计数都清零。
5. **检查点存进 MySQL**：配置 `gbi.hitl.checkpoint=mysql` 后，用框架自带的 `MysqlSaver`，存在元数据库的 `GRAPH_CHECKPOINT` / `GRAPH_THREAD` 表里。默认仍是内存，和原版一致。
6. 审核节点每次都会输出一句提示（已确认 / 已采用修改 / 第 n/3 次重新规划 / 已达上限），前端和测试记录都能看到发生了什么。

## 4. 为什么这么做（以及没选的方案）

**用 `interruptBefore` 暂停，而不是在节点里阻塞等待。** 阻塞会占着线程和 SSE 连接，审核人可能半小时后才回来。暂停后，状态全在检查点里，线程立即释放；恢复时用同一个 threadId 继续执行。这也是 LangGraph 和 Spring AI Alibaba Graph 推荐的人机协作模式。

**修改用"结构化的计划 JSON"，而不只是"自然语言修改意见"。** 自然语言意见要再过一次 LLM，模型可能顺手改坏别的步骤。直接改 JSON，审核人改了什么就执行什么，可预期、可审计。两种都保留：会改 JSON 的人直接改；只会描述的人就驳回并写原因。

**检查点选 MySQL，没选 Redis 或文件。**
- 元数据库本来就有，不新增组件。
- 审核记录本身就是审计数据，适合落库。
- 框架自带 `MysqlSaver`，不用自己实现序列化。

Redis 更快，但多一个依赖，而且要考虑过期策略；文件（`FileSystemSaver`）在多实例下不共享。默认仍保持内存，是为了不改变原版的零依赖启动体验。

**上限为什么是 3。** 这是产品取舍：驳回 3 次还不满意，通常说明问题本身没说清楚，或者数据不支持，继续让模型猜只是在烧钱。所以停下来，请用户换个问法。上限可以配置。

**驳回意见为什么累积。** 审核人连续驳回时，后一条通常是在前一条基础上补充，而不是推翻。只传最新一条，模型会"改了这个忘了那个"，实测原版就是这样。

## 5. 验证

- **单测 9 个**：等待、确认、修改、修改解析失败、驳回、第 3 次仍可确认、第 4 次结束、累积意见、结构修复不占驳回预算。全量单测通过。
- **端到端记录**（`results/step5/`，真实后端和模型）：
  - 确认、修改、连续驳回到上限，三个场景全部按预期走完。
  - 修改后执行的 SQL 只查华东；驳回后的计划同时满足此前全部意见。
  - **重启后恢复**：内存断点下，重启后用同一个 threadId 确认没有任何输出（状态丢了）；MySQL 断点下，重启后确认能完整执行到报告，耗时 132.7 秒。

## 6. 可能被追问的问题

- **审核期间库里的数据变了怎么办？** 计划只描述"查什么"，SQL 在确认之后才生成和执行，所以总是查到最新数据。
- **怎么防止审核人把计划改成危险操作？** 修改后的计划仍要过 `PlanExecutorNode` 的结构校验；生成的 SQL 还要过 Step 4 的守卫（只读、白名单），以及只读账号。
- **多实例部署时，SSE 连接在 A 实例，恢复请求打到 B 实例怎么办？** 有了 MySQL 检查点，B 实例能读到图状态并继续执行，结果推给发恢复请求的那个连接。原版的检查点在内存里，这种情况会直接失败。
- **checkpoint 会无限增长吗？** 会。生产环境需要按时间清理已结束线程的检查点，这一步还没做。
