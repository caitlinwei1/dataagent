# Step 4：SQL 只读守卫与错误分类的设计与取舍

> 面向面试复盘：做了什么、为什么这么做、考虑过哪些别的方案、解决了什么问题、怎么量化。

## 1. 要解决的问题

SQL 是 LLM 生成的，直接拿去连企业库执行有三类风险：

1. **安全**：模型可能写出 `DELETE`、`UPDATE`、`DROP`；被提示注入时，可能读系统表、读别的库，例如元数据库里存着模型的 API Key；`SLEEP()` / `pg_sleep()` 这类函数能把库拖死。
2. **越权**：Agent 只被授权分析一部分表，模型却可能用到别的表。
3. **失败后不知道怎么改**：原版执行失败时只把数据库报错原文丢回给模型重写。模型不知道错在"选错表"、"写错方言"还是"执行环境问题"，重试效率低，评测时也没法按原因拆分失败。

## 2. 原版 b297203 已经有的

- `SqlExecutor`：`setQueryTimeout(30)`、`setMaxRows(1000)`。
- `SemanticConsistencyNode`：用 LLM 检查 SQL 是否回答了问题，也就是"语义一致性"。
- 执行失败后，经 `SQLExecutorDispatcher` 回到 `SqlGenerateNode` 重写，最多 `max-sql-retry-count` 次。

**原版没有**：语句类型检查、表白名单、字段存在性检查、只读连接、错误分类。

## 3. 怎么做的：四项校验 + 三层兜底

执行前的四项校验：

| 校验 | 实现 | 不通过时归为 |
|---|---|---|
| 语法 | JSqlParser 解析，必须恰好一条语句 | 方言 |
| 语义一致性 | 原版的 `SemanticConsistencyNode`（LLM） | 交回重写 |
| 表白名单 | 解析出全部表名（含子查询、CTE、UNION），必须在 Agent 选定的表里，不许带系统库、不许跨库 | 选表 |
| 只读 | 只允许 SELECT；不许 `SELECT INTO`、`FOR UPDATE` / `LOCK IN SHARE MODE`、写操作 CTE，也不许调用黑名单函数（sleep、读文件、dblink、改配置、杀会话等） | 安全 |

外加一项"字段存在性"：带表别名的字段必须在召回到的表结构里，归为选表。

执行时的三层兜底，任何一层失守都不至于出事：

1. **只读账号**：数据源用 `gbi_reader` 连接，MySQL 只有 `SELECT, SHOW VIEW`；PostgreSQL 角色默认只读事务，`statement_timeout=30s`。
2. **只读连接**：每次执行前 `connection.setReadOnly(true)`。
3. **超时与行数**：30 秒超时（沿用原版，已用测试证明只读账号下也能真正中断查询），最多返回 1000 行。

执行报错时，`SqlErrorClassifier` 按 SQLState / 厂商错误码归类：

| 类别 | MySQL | PostgreSQL / Hologres / ADB-PG |
|---|---|---|
| 选表 | 1146 表不存在、1054 字段不存在、1052 字段有歧义 | 42P01、42703、42702 |
| 方言 | 1064 语法、1305 函数不存在、1055 ONLY_FULL_GROUP_BY、**1370** | 42601、42883 函数不存在、42803 GROUP BY、42804 类型 |
| 执行 | 超时、权限、连接、除零等其余错误 | 57014 超时、42501 权限等 |

1370 是一个实测出来的细节：只读账号调用 MySQL 没有的函数（比如 PostgreSQL 的 `date_trunc`）时，MySQL 会先把它当存储过程去检查 EXECUTE 权限，报的是"权限不足"而不是"函数不存在"。按字面归为执行错误就错了，它其实是方言问题。

拦截或报错时，返回给 SQL 生成节点的提示带上类别，例如 `SQL守卫拦截[WHITELIST/选表]：表不在白名单：trd_orders`，这样模型知道往哪个方向改。

## 4. 为什么这么做（以及没选的方案）

**解析器：选 JSqlParser，没选 Druid WallFilter，也没用正则。**
- 正则挡不住 `SELECT 1; DROP …`、注释里藏语句、写操作 CTE 这类变体，误杀也多，比如字段名 `updated_time` 里含 update。
- Druid 的 WallFilter 是现成的 SQL 防火墙，而且项目已经依赖 Druid。但它是连接池层面的过滤器，拿不到 Agent 级的表白名单，也没法把拦截原因结构化地交还给 LLM。
- JSqlParser 能拿到完整的语法树，同时支持 MySQL 和 PostgreSQL 的写法。RuoYi-Cloud-Plus 的数据权限（行级过滤）用的也是它，后面做行级权限时可以复用同一棵树。

**解析失败时一律拒绝（fail closed）。** 不认识的语句宁可不执行。为了让重写提示有用，解析失败时如果文本里有写关键字，就归为"只读"而不是"语法"。

**只读不能只靠守卫，所以做了三层。** 守卫的价值是"拦下并告诉模型原因"；真正的安全边界是数据库账号权限。面试时可以讲：应用层校验是第一道，账号权限才是最后一道。

**白名单用 Agent 选定的表，而不是召回到的前 K 张表。** 召回的表是给 LLM 的上下文，不是权限边界。用召回结果当白名单，召回漏一张表就会把正确的 SQL 也拦掉。

**字段检查只查带别名的字段，以及单表查询里的裸字段。** 多表查询里的裸字段可能属于任意一张表，也可能是 SELECT 里起的别名；硬查会误杀，所以宁可放过、交给数据库报错再分类。

**语义一致性仍交给 LLM。** "SQL 是否回答了问题"没法靠规则判断。原版已有这个节点，我们保留它，只补上确定性的检查。

**没做的**：自动加 LIMIT 改写 SQL。原版已经用 `setMaxRows` 限制返回行数，改写 SQL 会让用户看到的 SQL 和实际执行的不一致。

## 5. 量化

| 测试 | 结果 |
|---|---|
| 75 条正反例（30 条正常 SQL 已在真实库上执行通过；45 条攻击或错误 SQL） | 75/75 与标注一致：误拦 0/30，攻击拦截 28/28，越权和不存在的表 8/8，错字段 5/5，语法错 4/4 |
| 守卫耗时 | 平均每条 3 毫秒，对一次 LLM 调用（秒级）可以忽略 |
| 错误分类（真实 MySQL + PostgreSQL 各 7 种报错） | 14/14 |
| 超时 | 只读账号下 `SLEEP(5)` / `pg_sleep(5)` 在设置的 1 秒超时后被中断 |

**诚实说明**：用例和守卫是同一个人写的，第一次跑有 7 条不一致（6 条攻击被归成了"语法"，但都拦住了；1 条正常 SQL 被误拦），修复后才是 75/75。这个数字说明规则覆盖了已知的攻击类型，不能代表在 LLM 实际生成的 SQL 上的误拦率。Step 7 会在 320 题上统计：守卫拦截次数、拦截后重写成功率、执行失败按三类的分布，以及 SQL 执行成功率开启守卫前后的变化。

## 6. 可能被追问的问题

- **为什么不直接给只读账号就够了？** 账号只读能防写，但防不了读系统库、跨库读敏感表（元数据库里的 API Key）、`SLEEP` 拖库，也给不出可以回传给模型的拒绝原因。
- **JSqlParser 解析不了某些方言语法怎么办？** 默认拒绝（fail closed），并归为方言错误让模型换种写法。Hologres / ADB-PG 兼容 PostgreSQL 语法，大部分能解析；真的遇到解析器不支持的合法语法，再按数据源类型加白名单语法。
- **白名单和行级权限的关系？** 白名单管"能查哪些表"，行级权限管"能看到哪些行"（比如店长只能看自己店）。后者计划按 RuoYi-Cloud-Plus 的做法，用 JSqlParser 给每个 SELECT 的 WHERE 自动拼上过滤条件，和本守卫共用一棵语法树。
- **错误分类有什么用？** 一是重写提示更具体；二是评测时能拆出"选表错误"占比，直接反哺 Step 3 的召回；三是"方言错误"高说明提示词里的方言说明不够。
