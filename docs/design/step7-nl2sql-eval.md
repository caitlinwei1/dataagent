# 第 7 步：320 题问数评测集与执行准确率

## 1. 解决什么问题

前 6 步每一步都有局部指标：召回 Recall@5、守卫的 75 个用例、HITL 的端到端记录、沙箱的 9 个用例。
但用户只关心一件事：**问一句话，最后拿到的数对不对**。所以需要一个端到端的评测，用来回答三个问题：

1. 整条链路（意图 → 召回 → 规划 → SQL → 校验 → 执行 → Python → 报告）的成功率是多少？卡在哪一环？
2. 每一处改动（召回、守卫、时间口径）到底让结果变好了多少？
3. 迭代时会不会对着评测集“调参”？需要一份没被看过的 holdout 集来证明泛化。

## 2. 怎么做的

**出题**（`eval/nl2sql/build_questions.py`）

题集是 80 个题族 × 4 组参数，共 320 题。题族就是“问题模板 + 标准 SQL 模板”，参数包括月份、大区、类目、平台、仓库、TopN 的 N。题目覆盖两个维度：

- 意图：参照文章的 5 类意图，TopN、聚合、对比、趋势、下钻，各 64 题。
- 任务类型：单表、多表（含交易加履约的跨域）、多轮追问、多步分析，共 4 类。

dev 和 holdout **按题族切分，同时按月份切分**：

| 划分 | 题数 | 月份 |
|---|---|---|
| dev | 192 题 | 2026-02/03 |
| holdout | 128 题 | 2026-04 |

所以 holdout 的题型和时间都没有出现在 dev 里。

每个标准 SQL 都在 MySQL 上跑过：结果不能为空；TopN 在第 N 名出现并列时，把并列的行都记录下来。

**运行**（`eval/scripts/run_nl2sql.py`）

- 每道题开一个新会话，`threadId` 就是 conversationId。
- 多轮题先在同一个会话里把前面几轮问完，只给最后一轮打分。
- 单表、多表、多轮题走 `nl2sqlOnly`；多步题走完整流程，关闭人工审核。
- 每道题保存完整的 SSE 流，从里面抽出这些信息：计划步数和工具、每一次生成的 SQL、每一次守卫拦截和执行错误及其分类、最终结果集、总耗时和首次输出时间。

所以任何一道题都能从 conversationId 还原出“计划 → SQL → 修复了几次 → 为什么失败”。

**打分**：比较执行结果，不比较 SQL 文本，规则见 `eval/nl2sql/README.md`。

**本步的修复（来自 dev 冒烟测试的错误分析）**

- `TimeRangeHints` 把问题和多轮上下文里的时间表达，按日历精确换算成半开区间，以【时间口径】的形式加到 evidence 里，后续所有提示词都能看到。支持的表达有：2026年2月、2025年、2025年10月到2026年4月、第四季度、下半年、某日，以及去年同期、上个月/环比、近 N 个月。
- `SqlErrorClassifier.repairHint` 遇到“日期不存在”这类错误时，在重写提示里补一句具体该怎么改。
- 两者都可以用开关关闭（`gbi.nl2sql.time-hints`、`gbi.nl2sql.repair-hints`），方便做前后对比。

## 3. 为什么这么做（备选方案）

| 决策 | 选择 | 备选 | 为什么不选备选 |
|---|---|---|---|
| 怎么判对错 | 执行结果比对（EX），对列名、列顺序、取整、标签写法宽容 | 比对 SQL 文本（Exact Match） | 同一个问题有很多种正确写法，比如用 `trd_order` 还是日汇总表、用 JOIN 还是子查询，文本比对会大量误判 |
| | | 让大模型当裁判 | 不稳定，而且要额外花 token；只在报告类任务（第 8 步）用 |
| 题从哪来 | 题族模板 × 参数，人写标准 SQL，逐条执行验证 | 让大模型批量生成题目和 SQL | 标准 SQL 本身可能错，而且会带上生成模型的偏好 |
| | | 用 Spider/BIRD 这类公开集 | 业务和口径与电商场景无关，测不出术语、口径、跨域这些难点 |
| dev / holdout 怎么切 | 按题族和月份切 | 随机切 | 同一个模板的 4 个变体会同时出现在两边，holdout 等于泄题 |
| 时间怎么处理 | 系统按日历确定性地计算，注入提示词 | 让大模型自己推算日期 | 实测大模型会写出 `2026-02-29`；修复循环看到的问题改写里仍然是“至2026-02-29”，于是连续 10 次生成同一个错误日期 |
| | | 让执行层自动纠正非法日期 | 只能治标，而且会悄悄改变语义 |
| 前后对比怎么做 | 两个后端并排跑同一道题、同一个模型 | 先跑完一套配置，再跑另一套 | 免费额度用完后中途换了模型，前后两段就没法比了；配对跑可以保证每一对都可比 |

## 4. 量化结果

**完整的 320 题还没跑。** qwen3.8-flash 的免费额度用完了，caitlin 选择先跑 40 题配对样本：每个“任务类型 × 意图”格子取 dev 和 holdout 各 1 题，模型是 qwen-plus。

| 指标 | 原版召回 | 当前系统（v2） |
|---|---|---|
| SQL 执行成功率（30 道 SQL 题） | 86.7% | **100%** |
| 首次生成即执行成功 | 76.7% | **90.0%** |
| 执行准确率 EX | 50.0% | **56.7%** |
| 多表关联题 EX | 20% | 40% |
| 多步完成率（10 道多步题） | 60% | 60% |
| 选表类错误次数 | 33 | 10 |

冒烟测试里的单题效果：P01（“分析 2 月 GMV 环比并按大区拆解”）修复前 10 次生成 SQL 全部失败，没有出报告；修复后第 2 次生成就成功，报告也完成了。

**目标线**：holdout 执行准确率 ≥ 85%，来自需求文档，参照文章中“第一阶段核心查询 85%+”。现在 holdout 样本只有 15 道 SQL 题，EX 66.7%，**离目标还差很多**。
v2 答错的 13 道题已经按原因分好类，见 README。其中 5 道是类目层级问题：拿一级类目名去过滤三级的叶子类目。这一类可以用和【时间口径】一样的确定性提示来修，是下一步收益最大的方向。

## 5. 面试问答

- **执行准确率怎么算？为什么不比较 SQL 文本？** 见第 3 节第一行。比较的是结果集，对列名、列顺序、取整宽容，TopN 题只看实体。另外单独报一个严格版 EX（标签列也必须一致），两者都给出来。
- **怎么防止对着评测集调参？** dev 和 holdout 按题族加月份切分。修复只来自 dev 冒烟测试的 3 道题。为它们提供过线索的题已经从样本里排除。holdout 只用于最后验证。
- **“从多少提升到多少”是怎么得到的？** 两个后端并排跑：一个只关掉了新召回和第 7 步修复，另一个全开。同一道题、同一个模型，所以每一对结果都可比。
- **SQL 执行成功率和准确率为什么差这么多？** 能执行不等于对。剩下的错大多是口径错：类目层级、汇总表的粒度、大区归属。SQL 语法都没问题，但算的不是用户问的那个数。所以光看执行成功率会高估系统。
- **守卫拦截了 10 次，是误杀吗？** 不是。这 10 次都发生在原版召回那一组：召回没给对表，规划器就想用 `DESCRIBE` 去查表结构，守卫只允许 SELECT，按设计拦下了。换成新召回后拦截次数是 0。
- **为什么只跑了 40 题？** 免费额度用完了，这是 caitlin 的决定。脚本支持断点续跑，跑完整的 320 题只需要一条命令。所以对外的说法是：方法和工具链已经完整，规模化的数字还在补。
