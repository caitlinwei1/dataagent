# Step 3：Schema 召回（选表）的设计与取舍

> 面向面试复盘：做了什么、为什么这么做、考虑过哪些别的方案、解决了什么问题、指标从多少到多少。
> 数字全部是本仓库实测（`eval/table_select/README.md`），不是照抄目标值。

## 1. 要解决的问题

问数链路是"选表 → 写 SQL → 执行 → Python 分析 → 报告"。**选表错了，后面全错**，而且 LLM 写 SQL 时只能看到被选中的表，所以选表的召回率是整条链路的上限。

我们的库（电商经营 + 库存/仓储/履约）有 86 张表、1,146 个字段、312 条业务术语。企业库选表难在：

| 难点 | 例子 |
|---|---|
| 口语化 / 同义说法 | "卖了多少钱" → `trd_order.pay_amount`；"客单价" 是公式，不是字段 |
| 英文缩写表名、注释缺失 | 38 张表没注释时只剩 `wms_stk_mv` 这种名字 |
| 枚举值出现在问题里 | "华东""抖音""已签收" 是某列的取值，不是表名 |
| 桥接表不被点名 | 问"各店铺退款率"，要 `trd_order` 做中间表，但问题里不会提订单表 |
| 多轮追问 | "那按店铺拆开呢？"本身不含任何表的信息 |

**原版 DataAgent（b297203）的问题**：`SchemaService.getTableDocumentsByDatasource` 根本不看问题，查询词固定写死 `"default"`、只按数据源过滤、取前 10 条，排在前面的表取决于向量库存储顺序。实测 Recall@5 只有 5.6%（全注释）。

## 2. 怎么做的

`TableRecallService`：七路召回，各自出一个排好序的表名列表，用 **RRF（Reciprocal Rank Fusion，k=60）** 融合，取前 K 张表交给后面的节点。

| 通道 | 做法 | 针对的难点 |
|---|---|---|
| vector | 问题 embedding 与"表文档"（表名+注释）相似度 | 语义近似说法 |
| column | 与"列文档"相似度，列命中再汇总到表 | 问题提到的是字段而不是表 |
| keyword | BM25，词元 = 英文词 + 下划线切分 + 中文二元组 | 精确术语、缩写；不依赖向量接口 |
| term | 312 条口径/同义词，命中后映射到口径里写明的表 | "客单价""GMV" 这类指标口径 |
| value | 对低基数文本列（≤60 个取值）做 DISTINCT，问题里出现取值就召回该表 | "华东""抖音"等枚举值 |
| join | 取融合后前 3 张表作种子，沿逻辑外键补邻居表（种子保留在列表最前） | 不被点名的桥接表 |
| multiTurn | 把同一会话前几轮的问题拼到当前问题前 | 多轮追问 |

接入点：`SchemaRecallNode` 调用（`gbi.recall.enabled=true`），每个通道可以单独开关（`gbi.recall.<channel>`）。多轮上下文来自图状态里的 `MULTI_TURN_CONTEXT`。

## 3. 为什么这么做（以及没选的方案）

**融合：选 RRF，没选分数加权。** 各路分数尺度不同（余弦相似度、BM25 分、命中次数），直接加权要调权重，而且只能在评测集上调，等于在测试集上训练。RRF 只看名次，不需要调参。**学习排序（LTR）**需要标注数据训练，180 题太少。**LLM 直接选表**（把 86 张表全塞给模型）上下文长、慢、贵，结果也不稳定；更合理的位置是在召回之后做 rerank，这是下一步可以做的。

**关键词：选 BM25 + 中文二元组，没选 jieba 分词，也没上 Elasticsearch。** 领域词（"动销率""履约单"）不在通用词典里，二元组不需要词典就能匹配。ES 能做 BM25，但多部署一个重组件，而 1,232 个文档在内存里算 BM25 只要毫秒级。表多到几千张时，可以换成 Milvus 2.5 自带的 BM25 稀疏检索。

**口径单独做一路，而不是只靠向量。** "客单价 = 实付金额 / 支付订单数"是业务定义，向量模型不可能从表注释里学到。析言 GBI 的"业务知识/术语"也是单独管理的，这一步对齐的是它的产品设计。

**枚举值：数据库 DISTINCT，而不是把列样本全部向量化。** 枚举值的匹配是精确的字面匹配，向量化反而会把"华东"和"华南"拉得很近。只扫低基数文本列（≤60 个取值），跳过编号、手机号、URL 这类列，成本可控。XiYan-SQL 用 LSH 做值检索，适合高基数列，我们这里用不上。

**关联表：逻辑外键邻居，而不是全图最短路。** 种子只有 3 个，一跳邻居已经覆盖大部分桥接情况。Steiner 树这类连通子图算法更完整，但更复杂，而且会把整条路径上的表都塞进前 5。

**多轮：拼前几轮的问题，同时保留 QueryEnhance 的改写。** 只靠 LLM 改写，偶尔会把前一轮提到的表信息丢掉。拼接原问题成本为零，但上下文太长会稀释当前问题，所以只取用户问题、不取 AI 计划。

**向量库：选 Milvus，原版默认的 SimpleVectorStore 只保留为回退。**

| 方案 | 优点 | 缺点 |
|---|---|---|
| SimpleVectorStore（原版默认） | 零依赖 | 全在内存，只在正常关机时写 json；重启要重新向量化（约 20 分钟）；不能多实例共享 |
| **Milvus（选用）** | 专用向量库，HNSW 索引，支持 metadata 过滤和按条件删除，能独立扩容；2.5 版自带 BM25 | 多部署一个服务 |
| PGVector | 复用已有 PostgreSQL | 和业务库耦合；大规模下性能不如专用库 |
| Elasticsearch | 原版已带依赖，能做混合检索 | 资源占用大，向量检索不是它的强项 |

派生的 BM25 索引、枚举值索引和关联图**故意留在内存**：它们是从向量库和业务库算出来的，重建只要几秒；持久化反而多一份要同步的数据。真正需要的是"什么时候作废"：schema 重新初始化、逻辑外键增删改时发 `SchemaChangedEvent`，清掉对应的缓存。

**顺手修掉的原版问题**：启动时用 `hasDocuments(agentId)` 判断是否已初始化，但表结构文档只带 `datasourceId`、不带 `agentId`，所以每次重启都会重新向量化整个库，换成 Milvus 也一样。现在先检查该数据源所选的表是否都已有表向量。实测第二次启动 1 秒完成，不再调 embedding 接口。

## 4. 怎么评测

- **180 道独立选表题**：交易 36、供应链 36、商品 30、营销 30、财务 24、跨域 24；其中 13 道多轮。每题标注必需的表（金标）和题型。
- **指标**：
  - Recall@5 均值：每题 |金标 ∩ 前 5| / |金标| 的平均。
  - 全中率：前 5 张表包含全部金标的题目占比。
  - 另外报告 Recall@10。
- **为什么看 Recall 不看 Precision**：多召回一张无关表，LLM 写 SQL 时通常会忽略它；少召回一张必需的表，SQL 必错。为什么是前 5：控制上下文长度，和 SQL 生成节点实际放进 prompt 的表数一致。
- **注释消融**：复制一份库，去掉 38 张表的注释，看注释不全时各通道还剩多少作用。
- **逐通道累加**：每次加一个通道，看每一路贡献多少。另外单独跑一组去掉两个向量通道的配置，回答"embedding 到底有没有必要"。

## 5. 结果（SimpleVectorStore，qwen3.7-text-embedding）

| 配置 | 全注释 R@5 | 部分注释 R@5 |
|---|---|---|
| 原版 b297203（不看问题） | 5.6% | 7.9% |
| 只用向量（修复后） | 69.8% | 72.6% |
| + 列向量 | 74.9% | 77.0% |
| + 关键词 | 76.9% | 71.7% |
| + 口径 | 82.5% | 77.9% |
| + 枚举值 | 81.9% | 78.1% |
| + 关联表 | 84.5% | 81.4% |
| + 多轮（全通道） | **86.2%** | **82.0%** |
| 去掉向量通道 | 85.7% | 74.2% |

全通道的全中率：全注释 70.0%，部分注释 67.2%。Recall@10：95.0% / 93.7%。Milvus 上的复测见 `eval/table_select/README.md`。

**结论（面试时可以直接讲的）**
- 修复"不看问题"这个 bug 是最大的一步：5.6% → 69.8%。
- 多路召回再加 16 个点：69.8% → 86.2%。贡献最大的是口径（+5.6）和列向量（+5.1）。
- embedding 是否必要：注释齐全时几乎可以不要（85.7% vs 86.2%）；注释缺失时少了它掉 7.8 个点，缺注释的那批题从 66.7% 掉到 34.7%。所以保留 embedding。
- 已知缺陷：注释缺失时关键词通道反而拖 5.3 个点。没注释的表在 BM25 里几乎没有可匹配的词，等权融合时，有注释的近邻表被顶了上来。没有在这 180 题上调权重去修，留到 320 题的保留集上验证。

## 6. 踩过的坑

1. **编码**：MySQL 客户端默认 latin1，中文注释被双重编码，向量化的是乱码。现在所有 mysql 调用都带 `--default-character-set=utf8mb4`。
2. **关联表通道 v1**：扩展列表里没放种子表本身，RRF 时邻居每个都多拿一票，种子表反而被挤下去，全注释掉了 13 个点。修复：种子表排在扩展列表最前。
3. **口径被软删除**：全注释 agent 有 48 条口径（GMV、客单价……）处于删除状态，口径通道几乎没起作用。恢复后重跑。
4. **重启就重新向量化**：见第 3 节最后一段。

## 7. 诚实说明

- 口径和关联表两个通道，是看了这 180 题第一轮的漏召分布之后加的，所以没有干净的保留集，数字偏乐观。第 7 步的 320 题按 192 条开发集 / 128 条保留集隔离，保留集只跑一次。
- 目标值（例如 Recall@5 82.8% → 93.3%）只是参照，没有为了凑数去调参。实测全通道 86.2%，差 7 个点；剩下的漏召主要是订单表这类中心表。

## 8. 可能被追问的问题

- **RRF 的 k 为什么取 60？** 这是原论文的经验值，作用是让排名靠后的结果不至于完全没分。没有在评测集上调过。
- **为什么不直接让 LLM 选表？** 86 张表的 M-Schema 大约 2 万 token，每次提问都要全量送进去，又慢又贵；而且 LLM 选表的结果不可复现。召回负责"宽"，后面可以加一个 LLM rerank 负责"准"。
- **表规模到几千张怎么办？** 向量和 BM25 都交给 Milvus（稠密 + 稀疏混合检索）；按业务域先做路由，再在域内召回；关联表通道不受影响。
- **为什么部分注释的成绩有时比全注释还高？** 不同 agent 各自向量化，近邻排序有波动；另外第 6 节第 3 条的口径问题，修复前只影响全注释。最终对比以修复后的数字为准。
- **怎么保证评测不是自己骗自己？** 原版的数字保留；每个通道累加着测，能看出谁真有用；有消融对照；保留集只跑一次。
