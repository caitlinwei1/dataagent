# 06 ECharts + Markdown 报告，经 OpenAPI 对外

## 一句话讲法

> "上游的报告只能在聊天页的 SSE 流里看。我做了 `POST /openapi/v1/reports`，同步返回计划、Markdown、校验过的 ECharts JSON、状态和失败原因；报告末尾由系统附上实际执行的 SQL 和结果做证据，再做数字溯源。发现模型会把 -50% 写成 +0.74% 之后，改成由系统先算好合计给模型引用，这题由错变对。"

## 1. 原来有什么问题

1. **没法集成**：别的系统要报告，只能自己解析几十种节点消息的 SSE 流。
2. **不可核验**：数字从哪条 SQL 来，读者看不到。
3. **没法衡量**：没有报告任务集、没有人工基线。

## 2. Bad case 与根因（`eval/report/README.md`，8 题样本）

| Bad case | 根因 | 修复 / 现状 |
|---|---|---|
| **R07：SQL 是对的（实际 -50%），报告写成"+0.74%，平稳"，跑两次错两次** | 模型自己从结果表里做加减，搞混了两个月的数 | `ResultTotals`：系统给每步结果附"共 N 行，各数值列合计 = …"，prompt 要求合计和差值直接引用。修复后写的是 -49.98%，正确 |
| R40：UV 写成 93,216（正确 98,987） | 同上 | 同上修复后正确 |
| R01：元写成万元 | 单位换算 | `NumberTrace` 能标出来，没有自动修 |
| **R25：用 `created_time`（审计时间）过滤，查不到数据，又写出一份"看起来完整"的报告** | 数据集里故意留的陷阱；模型不知道业务时间是 `paid_at` | 全部 SQL 0 行时标为 `DEGRADED` 并写进 `issues`；step10 分支用规则提醒审计时间 |
| **R05（埋的根因：华东仓数码缺货）：计划写"通过 prd_spu 关联大区"，这条路径不存在；SQL 走了正确路径反而被语义校验驳回 10 次 → FAILED** | 语义校验以计划为准，计划错了 SQL 层无解 | **没修**。需要 SQL 层失败时回退到规划器 |
| R05 第二次运行：可行性评估判"需要澄清" | 归因题问"销量为什么跌"，根因在库存域；召回只围绕问题里的词，拿不到库存事实表 | **没修**。方向：假设驱动（先列可能原因域：缺货/价格/流量/履约，再分别召回） |
| 模型写 `formatter: function…` | ECharts option 里写 JS 函数，不是合法 JSON，前端渲染不了 | `ReportAssembler.charts()` 校验 JSON 且含 `series`，不合法不返回 |

## 3. 怎么解决的（代码）

- `dataagent/controller/ReportApiController.java`
  - `POST /openapi/v1/reports` `{agentId, question, threadId?, timeoutSeconds?}`：内部跑完整图（关闭人工审核），收集流，同步返回 `GbiReport`。
  - `GET /openapi/v1/reports/{threadId}`、`.../markdown`。
  - springdoc 注解生成 OpenAPI 3，导出到 `docs/api/openapi-reports.json`；`/swagger-ui.html`。
- `dataagent/service/report/ReportAssembler.assemble(threadId, question, seconds, chunks)`（纯函数，用真实流录像做单测）
  - `evidence`：每条**实际执行**的 SQL + 列名、行数、前 5 行；`appendix()` 渲染成"附录：数据证据"，**不经过 LLM**。
  - `charts()`：解析 ```echarts 代码块并校验。
  - `status`：COMPLETED / DEGRADED / FAILED；`issues`：Python 降级、全空结果、SQL 重试超限（哪一步、驳回几次、最后理由）、需要澄清。
- `NumberTrace.untraced(body, results)`：正文里 |x|≥100 的数（跳过百分数/年份/代码块，"万"换算），在证据里找出处：单元格、列合计、分组小计、同列两值之差，容差 0.5%，找不到列进 `untracedNumbers`。
- `ResultTotals.describe(resultJson)`：在 `ReportGeneratorNode` 里给每步结果加合计。

## 4. 为什么这么做

| 决策 | 选择 | 备选 | 为什么没选 |
|---|---|---|---|
| 接口形态 | 同步 REST + 按 threadId 查询 | 直接暴露 SSE | 调用方要理解几十种消息 |
| | | 异步任务 + 回调 | 调用方要实现回调；同步 + 超时 + 可查询已够用，以后可加 |
| 文档 | springdoc 从注解生成 | 手写 YAML | 会和代码脱节 |
| 证据 | 系统附上实际 SQL 和结果 | prompt 要求模型引用 SQL | 模型会漏引错引 |
| 核数 | 确定性溯源 + 系统预算合计 | 让 LLM 自查 | 同一个模型刚写错，再查可靠性不高 |
| | | 全模板化、不让模型写数 | 最可靠但报告僵硬；折中是把加法从模型手里拿走 |
| 图表 | 正文内嵌 ECharts option JSON | 后端渲染图片 | 不能交互、不能换主题 |
| 质量评估 | 规则：关键事实命中、根因点名、图表合法、证据、溯源 | LLM 打分 | 不稳定；R07 这种结构完整、语气专业但结论反了的，LLM 打分很可能给高分 |

## 5. 难点

- **数字溯源的误报/漏报**：单位换算、均值、建议里的假设数字会误报；"写了一个存在但用错地方的数"会漏报。所以溯源只是"标出可疑"，真正的修复是把计算从模型手里拿走。
- **"看起来完整的空报告"**：比报错更危险，必须显式标 DEGRADED。

## 6. 效果（8 题样本，qwen-plus）

| 指标 | 结果 | 性质 |
|---|---|---|
| 完成率 | 3/8（另 2 降级：1 Python、1 全空；3 失败） | 实测，样本极小 |
| 完成报告：合法图表 / 证据附录 / 结论建议 | 3/3 / 3/3 / 3/3 | 实测 |
| 关键事实命中 | 2/3 | 实测 |
| 埋的根因被点出 | **0/2**（都在 SQL 阶段失败） | 实测 |
| 数字溯源 | 171 个金额数字中 26 个无出处；人工核对 8 个确实写错 | 实测 |
| 数字完全正确的报告 | 1/3 | 实测 |
| R07 / R40 | 错 → 对（`ResultTotals`） | 实测，只是两题重跑 |
| 平均耗时 | 系统 5.0 分钟 vs 人工 64.3 分钟 | **系统实测，人工是按规则估算**（10 分钟理解 + 每条 SQL 8 分钟 + 每张图 5 分钟 + 写作 10 分钟 + 归因 10 分钟） |
| 40 个任务全量 | **没跑** | 补法：`python3 eval/scripts/run_reports.py --run full --all`；人工基线实测 2~3 题校准系数 |

**说"节省 92% 时间"一定要加前提**：人工是估算，而且 8 题里只有 1 份数字全对，实际节省要扣掉核对时间。

## 7. 追问

1. **报告要 5 分钟，同步接口不会超时吗？** 超时可配；超时后仍可按 threadId 查结果；大规模调用再加异步提交。
2. **怎么保证报告里的数可信？** 三层：系统证据附录、数字溯源标可疑、状态显式（空结果/降级/失败）。再加上合计由系统算。
3. **完成率 3/8 怎么看？** 8 题不是稳定比率；重要的是失败分得清（SQL 卡死、计划和校验矛盾、抄错数），每类都有修复方向，接口把原因写进 `issues`。
4. **归因题为什么难？** 问题问"为什么跌"，根因在问题没提到的业务域；召回和规划都围绕问题里的词展开。要做假设驱动的规划。
5. **为什么不用 LLM 给报告打分？** R07 就是反例。
