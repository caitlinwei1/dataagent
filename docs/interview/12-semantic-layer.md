# 12 借鉴语义层：把口径从"提示"变成"合约"

> 接 [11](11-b4-b6-root-cause.md)。11 里 B5、B6 的修法都是"往证据里写口径"，模型可以不听；B6 最后还剩一个没解决的问题：步骤失败时报告会编数。这一页借鉴大淘宝直播技术团队的文章《AI 时代的数据研发：Semantic（语义层）带来的工业革命》（2026-11-27），做了四件事，并在 B1~B10 上回放。
>
> 数据都是模拟数据（见 10 的边界说明）。回放用 qwen-plus，经网关 + 鉴权，记录在 `results/baozun/B*.sem-*.json`；离线校验在 `results/semantic/offline_check.json`。

## 一句话讲法

> 我看了淘宝直播数据团队的语义层实践，核心观点是"口径不能靠模型理解得聪明，要靠语义定义、查询约束和执行证据来保证"。我没有照搬他们的 DSL2SQL，而是做了一个最小可执行版：把最容易出错的 7 个指标写成**口径合约**，SQL 执行前用 JSqlParser 做确定性检查；同一个指标按**品牌合同和角色**解析出不同口径；用到汇总表时自动**拿明细对账**；报告加**证据台账**，步骤失败就写"受阻"，不许编数。离线 330 条标准 SQL 误报 0，历史上 17 条错 SQL 全部拦下；回放 B1~B10 全部答对，B6 的归因第一次三项全对。

## 文章做了什么，我们借了什么

| 文章的做法 | 我们的版本 | 没照搬的原因 |
|---|---|---|
| 禁止手写 SQL：指标/维度经语义层校验 → DSL2SQL 生成 → 只读执行 | **口径合约 + 执行前检查**（`MetricRuleChecker`）：模型照样写 SQL，但计算合约指标的 SQL 必须满足合约；漏了条件且模型改不对时，由系统确定性补上 | 他们有现成的指标平台和上百个业务方；我们 44 个指标、长尾问题多（320 题里只有 104 题命中合约指标），全量 DSL 成本高，且会丢掉 NL2SQL 对长尾的覆盖 |
| 语义请求在 SQL 之前校验口径、粒度、过滤 | 同上，检查点放在 SQL 守卫之后、权限改写之前 | — |
| 口径台账跨业务方共享，产物按业务方隔离；双层画像 | **同一指标按品牌合同 / 角色解析不同口径**（`MetricContractResolver`），品牌从数据权限推出 | 群聊入口、画像在我们这里没有对应场景 |
| 双引擎对账，"零行 / 失败 = 未定" | **汇总表 vs 明细对账**（`SummaryReconciler`）；报告里**零行 = 未定，失败 = 受阻**（`EvidenceLedger`） | 只有一个引擎，但"汇总 vs 明细"是宝尊这类数仓真实存在的同一类问题 |
| 缺口挂账，不许补齐；结果分已确认 / 待确认 / 受阻 | 报告证据台账 + 出处核对 + 一次重写 + 页脚列出无出处内容 | — |
| 入湖分区完整性、多 Agent 分工、OLAP 资产分级、记忆晋升 | **只口头讲**（见最后一节） | 没有真实湖仓、真实用户调用日志；硬做会是假数据 |

## 1. 口径合约 + 执行前检查

### 原来的问题
口径写在术语表里，以"证据"形式进 prompt。11 里证明了这条路的两个弱点：证据会被别的条目挤掉（B5、B6 已用"字面命中保底"缓解），以及**进了证据模型也可以不听**。

### bad case + 根因
| 例子 | 模型写的 SQL | 错在哪 | 后果 |
|---|---|---|---|
| B5 r3 | GMV 加了 `order_status IN ('PAID','SHIPPED','COMPLETED')` | GMV 不按状态过滤 | 少 1.3% |
| B5 after2 | 双11 GMV 没关联 `trd_presale_order` | 预售单按尾款时间归属 | 852,227.60（应为 956,004.20） |
| B6 r1~r3 | 销售额用 `trd_daily_shop_sales.paid_amount` | 汇总表含支付后关闭的单 | -19.5%（应为 -63.8%），根因被抹平 |
| B2 修复前 | 收入按 `settled_at` 过滤 | 收入按业务月 `month_key` | 取到 2 月的账 |

共同点：**错误都能从 SQL 文本上直接看出来**（用了哪张表的哪列、对哪列加了过滤），不需要执行，也不需要模型判断。

### 怎么做的
`gbi-agent/src/main/resources/gbi/metric-contracts.yml` 里每个指标写：触发词、定义、适用范围、规则。规则只有 6 种，全是从 SQL 上读得出来的：

| 规则 | 含义 | 例子 |
|---|---|---|
| `forbid_sources` | 不许引用这些列 | 销售额不许用 `trd_daily_shop_sales.paid_amount` |
| `forbid_filters` | 不许在 WHERE / ON / HAVING 里过滤这些列 | GMV 不许过滤 `order_status` |
| `require_mention` | 必须处理这些列（条件或分组） | 销售额必须处理 `order_status` |
| `require_any_source` | 至少引用其中一列 | 收入必须来自 `fin_settlement.revenue_amount` |
| `require_literal` | SQL 里必须出现的字面量 | 青岚不含税口径的 `1.13` |
| `when_aggregates` / `question_pattern` | 规则的适用条件 | 只在聚合了 `pay_amount` 时检查；只在问题里有具体日期时检查 |

流程（`SqlExecuteNode`）：SQL 守卫通过后 → `MetricRuleChecker.check()` → 违规就带着合约的提示回到 SQL 生成（每步最多 2 次）→ **模型拿到提示后第二次还漏同一个条件，且规则有 `fix`，系统直接把条件补进 WHERE**（`autoFix`，用该表在 SQL 里的别名）→ 补完重新检查、重新过守卫 → 执行。用错表、用错列不自动改，只能退回重写；2 次后仍违规就执行，但结果标"口径待确认"，报告台账会写出来。

### 为什么这么做
| 方案 | 为什么不选 / 选 |
|---|---|
| 继续往证据里写更多口径 | 11 已经证明证据可以被忽略，且写得越像问题越容易被错召回 |
| 让 LLM 语义校验节点判断口径 | 10 / 11 里它是最吵的节点（B4 把对的 SQL 驳回 2 次），而且不稳定 |
| 全量 DSL2SQL（文章的做法） | 最准，但 44 个指标全建模 + 长尾问题回退，成本是这一版的几倍；面试时可以说"指标再多会往这边走" |
| **合约规则 + 确定性补齐（选这个）** | 只对有 bad case 的 7 个指标写规则；检查是确定的、可单测的；"补条件"是 DSL 思路里最小、最安全的一块 |

### 效果（离线，不调模型，`MetricRuleOfflineEvalTest`）
| 指标 | 数字 |
|---|---|
| 320 问数 + 10 个宝尊例子的标准 SQL 误报 | **0 / 330**（其中 104 条命中合约指标） |
| 例子里的典型错 SQL 拦截 | **6 / 6**（B2、B3、B4、B5、B8、B9） |
| 历次回放里 agent 实际执行过的 SQL | **68 条中标记 17 条，17 条都对应当时的错答案**（B2 修复前、B5 r2/r3/after2、B6 的汇总表 SQL、B8/B9 修复前） |

## 2. 同一个指标，按品牌合同 / 角色解析不同口径

### 原来的问题
宝尊这样的代运营公司，同一句"销售额"在三方眼里不一样：品牌方按合同口径（例如不含税）考核，财务看退款后净额，店铺运营看实付。系统原来只有一个"通用口径"。

### bad case（修复前，PR #13 代码，`B8.pr13` / `B9.pr13`）
| 例子 | 谁问 | 问题 | 修复前 | 应该是 |
|---|---|---|---|---|
| B8 | 青岚品牌运营（`qinglan_ops`） | 2026年3月我们品牌的销售额是多少？ | 131,372.28（含税实付） | **116,258.65**（合同口径：实付 / 1.13，不含税） |
| B9 | 财务（`finance`） | 2026年3月各店铺的销售额分别是多少？ | 星屿抖音 372,285.48 …（实付） | **339,935.58** …（退款后净额，12 家店全部偏高 2%~13%） |

### 怎么做的
合约里每个指标可以有 `variants`，`when.brand` / `when.role`，第一个匹配的生效。`MetricContractResolver`：
- 品牌：问题里只点名一个品牌；或者**登录用户的行级权限只覆盖某个品牌的店**（青岚运营的部门绑定店 4、5 → 青岚）。所以品牌运营说"我们品牌"也能对上合同。
- 角色：网关转发的 RuoYi 角色 key（`finance`、`brand_ops`），现在进了图状态 `GBI_USER_ROLES`。
- 解析结果放在证据最前面，并写明"为什么用这个口径"；SQL 检查按同一份解析结果；报告页脚写出用了哪个口径。

### 为什么这么做
- 口径差异放在语义层，而不是让每个业务方各写一份术语：文章里叫"口径台账共享、产物隔离"。台账只有一份，变体挂在同一个指标下，改通用口径时变体一眼可见。
- 品牌从权限推，不从问题文字猜：品牌运营根本不会在问题里写品牌名；而权限是 B1 里已经验证过的确定信息。
- 两个品牌同时点名时退回通用口径，不替用户选。

### 效果（`B8.sem-r1`、`B9.sem-r1`）
| | 修复前 | 修复后 |
|---|---|---|
| B8 | 131,372.28 ✗ | **116,258.65 ✓**，SQL `SUM(pay_amount) / 1.13` |
| B9 | 12 家店都是实付 ✗ | **12 家店全部等于 net_sales ✓** |

## 3. 汇总表与明细对账

### 原来的问题
B6 的根因是"汇总表 `paid_amount` 含支付后被关闭的单"。11 里靠术语和表注释提醒模型别用汇总表算销售额。但用户问的如果本来就是"实付"（汇总表对这个口径是对的），一半金额来自缺货关单这件事就**没有任何地方会提示**。

### 怎么做的（`SummaryReconciler`）
SQL 成功读了 `trd_daily_shop_sales` 后：
1. 用 JSqlParser 把汇总表换成"同口径的明细聚合"派生表（**别名不变**，模型的 SQL 原样能跑），在用户的数据权限下再跑一次 → 汇总和明细不一致就提示（ETL 问题）。
2. 再跑一次只保留取消/关闭订单的版本 → 算出汇总数里来自这些订单的占比，超过 5% 就提示。
3. 提示写进结果的 note、流式输出和图状态，报告台账会带上。

为什么用"换表"而不是让模型再写一条对账 SQL：换表和 B1 的行级权限改写是同一个机制（`RowPermissionRewriter`），确定、不调模型，任何形状的 SQL 都能对上。

### 效果
| | 修复前（`B10.pr13`） | 修复后（`B10.sem-r1`） |
|---|---|---|
| 每日实付 | 对（但按店拆成 14 行） | 对（7 行，与标准答案一致） |
| 提示 | 无 | "paid_amount 合计 139,082.30 中，支付后被取消/关闭的订单贡献 76,637.57（**55.1%**）" |

正常月份不会误报：2026 年 3 月汇总与明细三项完全一致，关闭占比 1.6%，低于 5% 阈值。

## 4. 报告证据台账（P0：修 11 里没解决的"报告编数"）

### 原来的问题 / bad case
B6 after5：第 3 步（按仓库汇总缺货）的 Python 失败降级了，报告却写出"华东仓-**苏州中心仓**单仓贡献 **12 单（57.1%）**，缺货订单分布于 **7 个仓库**"。三个都是编的（真实是华东区域仓 23/23）。原来的 `NumberTrace` 只在 OpenAPI 报告路径上跑，而且只查 ≥100 的数，查不到"12 单""7 个仓库"和仓库名。

### 根因
报告节点拿到的是"所有步骤结果 + 一个要求写归因的计划"，没人告诉它哪一步失败了；它的任务是"写出原因"，缺数据时就补。

### 怎么做的（`EvidenceLedger` + `ReportGeneratorNode.generateTracedReport`）
1. **写之前**：每一步标状态——已完成 / 口径由系统补齐 / 口径待确认 / 未定（零行）/ 受阻（降级、失败）/ 未执行，连同规则写进报告 prompt：受阻和未执行的步骤不许给这一步的任何数字、名称或结论；零行写"未定"，不许写成 0。
2. **写之后**：金额（复用 `NumberTrace`）、小计数（"12 单""7 个仓库"，对照单元格、合计、行数）、仓库/店铺名，逐个到结果里找出处。
3. 有找不到的 → 带清单让模型重写一次 → 再核一次。
4. 页脚"证据核对（系统生成）"：每步状态、用了哪个口径、对账提示、仍然找不到出处的内容。不靠模型自觉，读者自己能看到。

### 为什么这么做
- 不在 prompt 里"禁止编造"了事：那是 11 之前的状态，after5 就是在这种 prompt 下编的。
- 重写只做一次：第二次还找不到的，标出来比无限重写可靠，也控制了耗时（每次重写约 60~70 秒）。
- 规则化的状态而不是让模型判断"哪步失败"：降级标记、零行都是确定信息。

### 效果
| | 修复前 | 修复后 |
|---|---|---|
| B6 after5 的编造内容（单测复现） | 苏州中心仓、12 单、7 个仓库没人发现 | 三个都被标出（`EvidenceLedgerTest`） |
| B6 回放：第一版报告里无出处的内容 | — | sem-v2：5 条 → 重写后 0 条；sem-r1：2 条 → 重写后 1 条（一个错误的推导合计 143,102.24，页脚标出） |
| 零行步骤 | 可能写成"没有发生" | sem-v2 第 5 步零行，报告写"该步未定（零行），结论未定" |

**诚实说明**：B1~B10 都是开发时用过的例子（B6 的"适用范围"就是看了回放才加的），这张表说明"这些 bad case 修掉了"，不是准确率。泛化的证据是离线那组数字（330 条标准 SQL 0 误报）；320 题的 holdout 还没用这一版跑。

**B6 r2 为什么没报告**：计划第 3 步写成"用第 2 步输出的 order_id"，模型把它写成 `IN (/* 步骤2输出的 order_id */)` 这种占位注释，Druid 拒绝带注释的 SQL，10 次都一样；重规划额度第 1 步已用掉，于是整轮 END，用户什么也拿不到。这和口径无关，是跨步传值的老问题。处理：多步计划里某个 SQL 步骤用完重试次数后，**不再结束整轮，而是把这一步记成"受阻"继续执行**，报告按台账写"该步受阻"（`SqlGenerateNode.skipBlockedStep`，`SqlStepBlockedTest`）。跨步传值本身没修。

**r3 暴露的两个漏洞（没修，面试时主动说）**：① 出处核对跳过了代码块，报告里 ECharts 饼图写了 `warehouse_id = 6/7/8` 的数，正文说仓库待确认，图里却有数；② 第 5 步 Python 输出的是"未找到相关数据"这种文字，台账按"有分析结论"记成已完成，应该识别成"未定"。

## 回放中踩的坑（面试可讲）

1. **模型连续 3 次不听提示**（`B6.sem-v1`）。第一版只有"违规 → 带提示重写，最多 2 次"。B6 第 1 步的计划写的是"这一步不要加 order_status 过滤"（归因模板要看关单），合约又要求"必须处理 order_status"，模型三次写出一模一样的 SQL，最后带着违规执行，环比又回到 -19.5%。→ 加了**确定性补齐**：模型拿到提示后第二次还漏，就由系统按合约补上条件。这正是文章"DSL 负责表达、不让模型猜"的最小版本。
2. **口径被套到了诊断步骤上**（`B6.sem-v2`）。合约证据说"销售额必须排除取消/关闭订单"，模型把这个条件加到了退款和缺货那两步，结果缺货关单的订单全被过滤掉，报告结论变成"没有缺货"——环比对了，原因反而丢了。→ 合约加 `scope`（适用范围）："这个排除只用于算销售额本身，查退款、查缺货、按状态拆分的步骤不要排除"。教训：**口径要写清楚管到哪里为止**，文章里"明确哪些口径归语义层、哪些属于上游加工或下游查询"说的就是这个。
3. **对账漏了没有表名前缀的列**（`B10.sem-v1`）。`select stat_date, paid_amount from trd_daily_shop_sales tds join dim_shop …`，列名没带别名，第一版以为可能属于别的表就跳过了。汇总表的列名（`paid_amount`、`gmv`）在这个库里是唯一的，改成不带前缀也算。
4. **第一版合同口径选了"不含运费"**，结果和通用口径只差 0.2%（满 99 包邮），演示不出差别；改成"不含税"（差 11.5%），这也是品牌方考核里更常见的约定。

## 追问

- **为什么不直接做 DSL2SQL？** 320 题里只有 104 题（约 1/3）命中这 7 个合约指标，长尾问题还得靠 NL2SQL。合约规则是"在 NL2SQL 外面加护栏"，DSL 是"换掉 NL2SQL"；先用护栏把有 bad case 的指标收住，指标多了再把高频指标迁到 DSL。
- **规则会不会误杀？** 离线 330 条标准 SQL 0 误报；规则都带适用条件（只在聚合了某列时、只在问题有日期时）。真误杀时最多重写 2 次，之后照常执行并标"口径待确认"，不会卡死。
- **自动补条件安全吗？** 只补"漏了某个过滤"这一类（`fix` 显式配置），补完重新走合约检查和 SQL 守卫；用错表、用错列不自动改。
- **品牌口径从权限推，权限错了怎么办？** 权限是网关签名过来的确定信息，B1 已经验证过 1,276/1,276 条行级改写一致；推不出来（多品牌、总部账号）就用通用口径，并在证据里写明原因。
- **出处核对会不会误报？** 会：比较、阈值类的话（"均未超过 ¥4,000"）也会被标出来。所以它不拦截报告，只重写一次 + 页脚标注，读者自己判断。

## 只适合口头讲的（文章里有，我们没做）

- **多平台数据到达时间不一致**（文章：分区完整性对账）：天猫、京东、抖音的 T+1 数据落库时间不同，取数前应检查每个平台每天的数据是否齐全，缺了标"未计入"。我们只做了单表的时效提示（B7）。
- **多 Agent 分工**（数据底座 / 语义层 / 业务分析）：本质是"出了问题能追到负责的那一层"。我们对应的是错误分类（选表 / 方言 / 执行 / 权限）+ 证据台账里的"受阻、未定、口径待确认"。
- **按调用量给资产分级（OLAP Tier）**：没有真实用户日志。能诚实说的是"按评测里的出错率找热点"，本页离线校验里的"历史 SQL 68 条标记 17 条"就是这个思路的雏形。
- **记忆晋升**（同一口径被纠正两次以上就固化）：对应 HITL 里用户改计划的记录，可以作为合约变体的来源；没做。
