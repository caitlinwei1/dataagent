# 01 Schema 召回（元数据 + 业务术语 + 列样本 + 多轮 + 枚举值，180 题 Recall@5）

## 一句话讲法

> "上游的选表根本不看问题，Recall@5 只有 5.6%。我先修了这个 bug 到 69.8%，再针对错题加了 6 路召回（列向量、BM25、业务口径、枚举值、外键补桥接表、多轮），用 RRF 按名次融合，到 86.2%；注释缺一半时还有 82.0%。"

## 1. 原来有什么问题

- 选表是整条链路的上限：SQL 生成只能看到被选中的表，选漏一张必需表，SQL 必错。
- 上游 b297203 的 `SchemaService.getTableDocumentsByDatasource`：查询词写死 `"default"`、相似度阈值 0、只按数据源过滤、取前 10 条。**排在前面的表取决于向量库里的存储顺序，和问题无关。** 每次重建索引顺序都变（第一轮测出来是 2.5%，第二轮 5.6%）。
- 就算修好，只用"表名+注释"的向量也有 5 类问题答不好（下一节）。

## 2. Bad case 与根因（全部来自 `eval/table_select` 的错题分析）

| Bad case 类型 | 例子 | 根因 | 对应的修复 |
|---|---|---|---|
| 问题和表毫无关系 | 任何一题 | 上游召回不看问题 | 修 bug：用问题做向量检索 |
| 口径/指标词 | "客单价""GMV""动销率" | 这是业务公式，表注释里没有，向量学不到 | **口径通道**：312 条术语，命中就映射到术语里写明的表 |
| 问的是字段不是表 | "卖了多少钱" → `trd_order.pay_amount` | 表级向量只看表名+表注释 | **列向量通道**：列命中汇总到表 |
| 枚举值 | "华东""抖音""已签收" | 是某列的取值，不是表名或注释 | **枚举值通道**：低基数文本列做 DISTINCT，字面命中 |
| 桥接表不被点名 | "各店铺退款率" 需要 `trd_order` 做中间表 | 问题里不会出现中间表 | **关联表通道**：前 3 张种子表沿逻辑外键补一跳邻居 |
| 多轮追问 | "那按店铺拆开呢？" | 本句不含任何表信息 | **多轮通道**：拼上同一会话前几轮的用户问题 |
| 注释缺失 | 38 张表去掉注释后只剩 `wms_stk_mv` | 只剩英文缩写 | 保留 embedding（消融证明它在缺注释时最值钱） |

剩下没解决的漏召（实测）：全注释下漏掉的 77 个金标表里，`trd_order` 23 次、`trd_order_item` 10 次、`prd_sku` 9 次、`dim_shop` 6 次，都是"中心表/桥接表"。

## 3. 怎么解决的（代码）

- `dataagent/service/schema/recall/TableRecallService.java`
  - `rank(agentId, datasourceId, query, context, channels)`：每路各出一个排好序的表名列表
  - `vectorTables` / `columnTables`：向量检索（表文档 / 列文档）
  - `index()` / `buildIndex()` / `tokens()`：BM25，词元 = 英文词 + 下划线切分 + **中文二元组**
  - `termTables`：口径通道；`valueIndex`：枚举值通道；`joinTables` + `adjacency`：外键邻居
  - `fuse()`：RRF，`score = Σ 1/(60 + rank)`
  - `onSchemaChanged` / `invalidate`：schema 重新初始化或外键变更时，清掉内存里的 BM25/枚举/关联图缓存
- 接入：`dataagent/workflow/node/SchemaRecallNode.java` 第 104 行，`gbi.recall.enabled=true` 时走新召回，多轮上下文用 `TableRecallService.previousQuestions(MULTI_TURN_CONTEXT)` 取。
- 每个通道单独开关 `gbi.recall.<channel>`，方便做逐通道消融。
- 向量库换成 Milvus（profile `milvus`），并修了"每次重启都重新向量化"的 bug。

## 4. 为什么这么做：备选方案

| 决策 | 选择 | 备选 | 为什么没选 |
|---|---|---|---|
| 多路怎么合并 | RRF（只看名次） | 分数加权 | 余弦、BM25、命中次数尺度不同；加权要调参，只能在评测集上调 = 在测试集上训练 |
| | | LTR 学习排序 | 要标注数据训练，180 题太少 |
| | | LLM 直接从 86 张表里选 | 86 张表 M-Schema 约 2 万 token，每题都送，慢、贵、不可复现。合理位置是召回之后做 rerank |
| 关键词 | BM25 + 中文二元组 | jieba 分词 | "动销率""履约单"不在通用词典，二元组不用词典 |
| | | Elasticsearch | 多一个重组件；1,232 个文档内存 BM25 毫秒级 |
| 枚举值 | DISTINCT 字面匹配，只扫 ≤60 个取值的文本列 | 把列样本向量化 | 向量会把"华东"和"华南"拉得很近，枚举要的是精确匹配 |
| | | XiYan-SQL 的 LSH 值检索 | 适合高基数列，这里用不上 |
| 桥接表 | 外键一跳邻居 | Steiner 树 / 全图最短路 | 更复杂，而且会把整条路径的表都挤进前 5 |
| 向量库 | Milvus | SimpleVectorStore（上游默认） | 全内存，重启要重新向量化约 20 分钟，不能多实例共享 |
| | | PGVector / ES | 和业务库耦合 / 资源大且向量不是强项 |
| 指标 | Recall@5（不看 Precision） | | 多一张无关表 LLM 通常忽略；少一张必需表 SQL 必错。5 = SQL 生成 prompt 实际放的表数 |

## 5. 技术难点与踩坑（都是真实发生过的，有记录）

1. **关联表通道 v1 反而掉 13 个点**（77.2% → 64.2%）：扩展列表里没放种子表本身，RRF 时邻居都多一票，种子被挤下去。修法：种子表排在扩展列表最前。记录在 `results/step3/join_v1/`。
2. **口径通道几乎无效（+0.1）**：查下来是 48 条口径（GMV、客单价……）在 agent 5 里被软删除了，只剩 264/312 条。恢复后 +5.6。记录在 `results/step3/glossary_264/`。
3. **中文注释乱码**：MySQL 客户端默认 latin1，向量化的是乱码。所有 mysql 调用加 `--default-character-set=utf8mb4` 后重新导入。
4. **每次重启都重新向量化**：上游用 `hasDocuments(agentId)` 判断，但表文档只带 `datasourceId` 不带 `agentId`，所以永远判为"没初始化"。改为检查该数据源选定的表是否都有向量，第二次启动 1 秒。
5. **BM25 在注释缺失时拖后腿**：部分注释库上 +keyword 反而 -5.3 点。没注释的表在 BM25 里没词可匹配，等权融合把有注释的近邻表顶上来。**没有修**（不想在 180 题上调权重），这是一个可以主动讲的已知缺陷。

## 6. 效果（全部实测，`eval/table_select/README.md`）

| 配置 | 全注释 R@5 | 部分注释 R@5 |
|---|---|---|
| 上游 b297203 | 5.6% | 7.9% |
| 修 bug，只用表向量 | 69.8% | 72.6% |
| + 列向量 | 74.9% | 77.0% |
| + BM25 | 76.9% | 71.7% |
| + 口径 | 82.5% | 77.9% |
| + 枚举值 | 81.9% | 78.1% |
| + 关联表 | 84.5% | 81.4% |
| + 多轮（全通道） | **86.2%** | **82.0%** |
| 全通道但去掉两个向量通道 | 85.7% | 74.2% |
| Milvus 复测（全通道） | 87.9% | 79.8% |

- 全中率（前 5 包含全部金标）70.0% / 67.2%；Recall@10 95.0% / 93.7%。
- 多轮题 13 道：56.9% → 80.3%。同义说法题：58.3% → 76.3%（口径通道）。
- **简历占位**：目标 93.3%（基线 82.8%）**没达到**，实测 86.2%。
- **怎么讲"从 X 到 Y"**：公平的基线是"修 bug 后只用向量"的 69.8%，不要拿 5.6% 当基线吹（面试官一听就知道是 bug）。推荐说法："bug 修复带来 5.6→69.8，多路召回再带来 69.8→86.2"。
- **干净度**：口径和关联表是看了错题才加的，180 题不是干净 holdout。补法：在 320 题的 128 道 holdout 上跑一次选表召回（`eval/scripts/run_table_select.py` 改成读 `eval/nl2sql/questions.jsonl` 的 holdout 子集，金标表可以从 gold SQL 用 JSqlParser/正则抽出来）。

## 7. 面试官可能追问

1. **RRF 的 k 为什么是 60？**
   原论文的经验值，作用是让排名靠后的结果不至于没分、排名靠前的不至于一家独大。我没在评测集上调它，就是为了不过拟合。
2. **为什么不直接让大模型选表？**
   86 张表的 M-Schema 约 2 万 token，每次都送又慢又贵，结果还不可复现。召回负责"宽"，后面可以加一个只看 Top-15 的 LLM rerank 负责"准"，这是我会做的下一步。
3. **表到几千张怎么办？**
   向量和 BM25 都交给 Milvus 2.5 的稠密+稀疏混合检索；先按业务域路由，再在域内召回；关联表通道不受规模影响。
4. **embedding 到底有没有必要？**
   做了消融：注释齐全时去掉向量几乎不掉（85.7 vs 86.2）；注释缺一半时掉 7.8 点，缺注释那批题从 66.7% 掉到 34.7%。真实企业库注释往往不全，所以保留。
5. **你怎么证明不是在自己骗自己？**
   上游数字保留；每个通道逐个累加测，能看到谁有用谁没用（枚举值通道基本持平，我就照实写）；有注释消融对照；而且我主动承认 180 题不是 holdout。
