# 04 SQL 生成 + 4 道校验 + 失败重写 + 错误分类

## 一句话讲法

> "SQL 用 Qwen 生成，执行前过 4 道检查：语法、语义一致性、表白名单、只读。语义靠 LLM，其余三道我用 JSqlParser 在语法树上做，平均 3 毫秒。拦下或执行报错时，按 SQLState/错误码分成选表、方言、执行三类，把原因交回模型重写。40 题配对实验里执行成功率 86.7% → 100%。"

## 1. 原来有什么问题

上游只有 `setQueryTimeout(30)`、`setMaxRows(1000)` 和一个 LLM 语义检查：

- **安全**：模型可能写 `DELETE/DROP`；被注入时可能读系统库或元数据库（里面存着模型 API Key）；`SLEEP()` 能拖库。
- **越权**：模型可能用到 agent 没被授权的表。
- **失败后不知道怎么改**：报错原文直接丢回去，模型不知道是选错表、方言错、还是环境问题；评测也没法按原因拆。

## 2. Bad case 与根因

| Bad case | 根因 | 修复 | 出处 |
|---|---|---|---|
| **P01 "2 月 GMV 环比按大区拆"：连续 10 次生成 `2026-02-29`，SQL 重试耗尽，没出报告** | 模型自己推算日期；修复循环里改写后的问题本身就写着"至 2026-02-29"，模型每次照抄；报错原文只说"日期非法"，没说怎么改 | `TimeRangeHints` 按日历算好半开区间（`>= '2026-02-01' AND < '2026-03-01'`）注入证据；`SqlErrorClassifier.repairHint` 对非法日期给具体改法。修复后**第 2 次**就成功 | `docs/design/step7-nl2sql-eval.md`，冒烟记录 |
| 只读账号调 PostgreSQL 的 `date_trunc`，MySQL 报"权限不足"（1370）而不是"函数不存在" | MySQL 遇到不认识的函数会先当存储过程检查 EXECUTE 权限 | 把 1370 归为**方言**而不是执行 | `SqlErrorClassifier`，step4 |
| 原版召回组里守卫拦了 10 次 `DESCRIBE` | 召回没给对表，规划器想去查表结构；守卫只允许 SELECT | 按设计拦截（不是误杀）；新召回组拦截 0 次 | step7 |
| 剩余 13 道答错题里 5 道：拿一级类目名去过滤订单明细上的**三级**类目 `category_id`，结果为空 | 口径错，不是语法错——SQL 能执行但算的不是用户要的数 | 主分支没修；step10 分支用"规则"注入 `c3→c2→c1` 关联路径 | `eval/nl2sql/README.md` |
| 守卫第一次跑 75 例有 7 条不一致（6 条攻击被归为"语法"但都拦住了，1 条正常 SQL 被误拦） | 解析失败时一律归"语法"，重写提示没用 | 解析失败但文本里有写关键字时归为"只读" | step4 |

## 3. 怎么解决的（代码）

- **生成**：`SqlGenerateNode` → `Nl2SqlServiceImpl`，prompt 里的 schema 是 M-Schema 风格（借鉴 XiYan-SQL 的格式），证据里有口径和时间口径。
- **语义一致性**：上游的 `SemanticConsistencyNode`（LLM），不通过回到生成。
- **守卫**：`dataagent/service/sql/guard/SqlGuard.check(sql, schema, whitelist, columns)`
  - 语法：JSqlParser 解析，必须**恰好一条**语句；解析失败 fail closed。
  - 只读：只允许 SELECT；用 visitor 拒绝 `Insert/Update/Delete/Merge/Upsert`（包括写操作 CTE）、`SELECT INTO`、`FOR UPDATE`、函数黑名单（sleep、读文件、dblink、改配置、杀会话）。
  - 白名单：`TablesNamesFinder` 风格的遍历，拿到子查询/CTE/UNION 里的所有表，必须在 agent 选定的表里，不许系统库和跨库。
  - 附加字段检查 `unknownColumn`：带别名的字段必须在召回到的表结构里（多表查询的裸字段不查，避免误杀）。
- **接入**：`SqlExecuteNode.guard()` 在执行前调用，`blocked()` 把 `SQL守卫拦截[WHITELIST/选表]：表不在白名单：trd_orders` 这样的反馈写进 `SQL_REGENERATE_REASON`，`SQLExecutorDispatcher` 看到失败就回 `SqlGenerateNode`。
- **执行**：只读账号 `gbi_reader`（MySQL 只有 SELECT、SHOW VIEW；PG 默认只读事务 + `statement_timeout`）+ `connection.setReadOnly(true)` + 30 s 超时 + 1000 行。
- **错误分类**：`SqlErrorClassifier.classify()` 按 SQLState / vendor code：
  - 选表：MySQL 1146/1054/1052，PG 42P01/42703/42702
  - 方言：1064/1305/1055/1370，PG 42601/42883/42803/42804
  - 执行：超时、权限、连接、除零等
- **重写上限**：`max-sql-retry-count: 10`（上游默认）。

## 4. 为什么这么做

| 决策 | 选择 | 备选 | 为什么没选 |
|---|---|---|---|
| 解析器 | JSqlParser | 正则 | 挡不住 `SELECT 1; DROP …`、注释藏语句、写操作 CTE；还会把 `updated_time` 当成 update |
| | | Druid WallFilter（项目已依赖） | 在连接池层，拿不到 agent 级白名单，也没法把原因结构化交回 LLM |
| 安全边界 | 三层：只读账号 + 只读连接 + 超时/行数 | 只靠守卫 | 守卫的价值是"拦下并告诉模型原因"；真正的边界是数据库权限 |
| 白名单来源 | agent 选定的表 | 召回到的 Top-K 表 | 召回漏一张表就会把正确 SQL 拦掉；召回是上下文不是权限 |
| 解析失败 | 拒绝（fail closed） | 放行 | 不认识的语句宁可不执行 |
| 语义一致性 | 保留 LLM | 规则 | "SQL 是否回答了问题"没法规则化 |
| 时间 | 系统按日历确定性计算 | 让执行层自动纠正非法日期 | 治标，而且悄悄改语义 |
| 自动加 LIMIT | 不做 | 改写 SQL | 用户看到的 SQL 和执行的不一致；`setMaxRows` 已经限了 |

## 5. 难点

- **遍历全面**：表可能藏在子查询、CTE、UNION、EXISTS、标量子查询、LATERAL 里；写操作可能藏在 CTE 里。用 JSqlParser 的 visitor 覆盖每种节点。
- **误拦 vs 漏拦的取舍**：字段检查只查带别名的字段，多表裸字段交给数据库报错再分类。
- **错误分类要按"该怎么改"分，而不是按错误码字面**（1370 是例子）。
- **两种方言**：MySQL 和 PG 的错误码映射都实测过；Hologres/ADB-PG 走 PG 映射（没有真实实例）。

| 指标 | 结果 | 性质 |
|---|---|---|
| 守卫 75 例（30 正常 SQL 在真实库跑通 + 45 攻击/错误） | 75/75 一致：误拦 0/30，攻击 28/28，越权表 8/8，错字段 5/5，语法 4/4 | 实测，但用例和守卫是同一人写的 |
| 守卫耗时 | 平均 3 ms/条 | 实测 |
| 错误分类（MySQL+PG 各 7 种真实报错） | 14/14 | 实测 |
| 40 题配对（qwen-plus，上游召回 vs v2）SQL 执行成功率 | **86.7% → 100%**（30 道 SQL 题） | 实测，样本小 |
| 首次即执行成功 | 76.7% → 90.0% | 实测 |
| 选表类错误次数 | 33 → 10 | 实测 |
| EX 执行准确率 | 50.0% → 56.7% | 实测 |
| "结果按指标/维度/时间窗校验" | **只做到一部分**：时间窗由时间口径保证；指标/维度靠 LLM 语义校验和口径证据；确定性的只有"结果全空 → DEGRADED"和报告数字溯源 | 缺口，见 99-gaps |
| 守卫拦截后重写成功率 / 三类错误分布（大样本） | 没在 320 题上统计 | 补法：跑完整 320 题后，从 trace 里统计 `sql_guard` 和 `errorClass` 日志 |

**注意说法**："执行成功率 100%"只代表"能执行"，EX 才是"算对"。面试官很可能追这个差距，主动讲。

## 7. 追问

1. **只读账号不就够了吗？** 只读防写，但防不了读系统库、跨库读元数据库里的 API Key、`SLEEP` 拖库，也给不出能回传给模型的原因。
2. **JSqlParser 解析不了的合法方言怎么办？** fail closed 并归为方言错误，让模型换写法；真遇到常见的不支持语法，再按数据源类型加白名单。
3. **执行成功率 100% 为什么 EX 只有 56.7%？** 能执行≠对。剩下的错主要是口径：类目层级（5）、汇总表粒度（3）、大区归属（2）、度量口径（2）、多轮指代（1）。SQL 都合法，但算的不是用户问的那个数。
4. **错误分类有什么用？** ① 重写提示更具体；② 评测时能拆出"选表错误"占比反哺召回；③ 方言错多说明 prompt 里方言说明不够。
5. **为什么用 Qwen 不用 XiYan-SQL 模型？** 实话：没部署 XiYan-SQL 模型（需要 GPU 自部署）；借鉴的是它的 M-Schema 格式和评测思路。如果要上，会做成多候选：Qwen 和 XiYan 各出一条，执行结果投票。
