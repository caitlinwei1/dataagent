# 10 落到宝尊：七个业务难点，问题在哪、方案对比、修复前后

> **先说清楚边界**：原型参照品牌电商服务商（以宝尊电商为例）的公开业务模式。品牌名（曜石、青岚……）、店铺和所有数据都是**虚构的模拟数据**，不代表任何公司的经营数据。面试说法："我参照品牌电商代运营公司的公开业务模式，模拟了一套数仓，在上面做问数 agent。"业务和数据背景见 [00 第 0 节](00-architecture.md)。
>
> 数据改动见 `dataset/README.md` 的 v2 一节。例子在 `eval/baozun/examples.jsonl`，运行脚本是 `eval/baozun/run_examples.py`，原始记录（SSE trace + 结果）在 `results/baozun/`：`B*.json` 是修复前，`B*.after*.json` 是修复后（`-r1/-r2/-r3` 是第几轮）。
>
> 运行条件：2026-11-21，模型 qwen-plus，v2 数据。修复前是 master 代码、每题 1 次；修复后经网关 + 鉴权（B1 用青岚运营账号登录，其余用 admin），B1/B2/B3/B7 各 1 次，B4/B5/B6 各 2~3 次。**单次运行有随机性**，下面的结论是"这类问题以前怎么错、现在怎么错"，不是准确率。

|---|---|---|---|---|---|

## B1 品牌数据隔离

**业务场景**：一个运营只服务青岚一个品牌。品牌之间是竞争对手，青岚的运营绝不能看到曜石的数据。这是服务商的合同义务。

**问题在哪**：master 上 `GraphServiceImpl` 起图时没有身份；`SqlExecuteNode` 拿到 SQL 直接执行。

**是什么**：SQL 本身没有错，错的是"谁在问"没有进入执行链路。鉴权和数据权限在分支 `claude/project-thread-alilb6` 上已经做完（见 09），但没合并；而且分支上的部门映射是"大区 → 店"，没有"品牌 → 店"。

**方案对比**

| 方案 | 做法 | 问题 |
|---|---|---|
| A. 提示词里告诉模型"只查 4、5 号店" | 把可见店铺写进 prompt | 一次注入就绕过；模型漏写 WHERE 就泄露 |
| B. 每个品牌一个库 / 一个视图 | 物理隔离 | 86 张表 × 品牌数，跨品牌的总部视角做不了 |
| C. 执行前改写 SQL（已有） | JSqlParser 把每个受限表替换成 `(SELECT * FROM t WHERE shop_id IN (…))` | 需要维护行策略；已在分支实测 1,276/1,276 一致 |

**选择**：C。理由在 09 第 4 节：模型现写的 SQL 不可信，只能在执行层强制；派生表替换和外层写法无关（往 WHERE 追加会把 LEFT JOIN 变成内连接）。品牌隔离不需要改代码，只是**换一种部门**：在 `ruoyi/sql/gbi_system.sql` 加部门 109"青岚品牌组"（绑定店 4、5）、角色 7"品牌运营"（`data_scope=3` 本部门）和用户 `qinglan_ops`。

**修复前后**（`B1.json` → `B1.after.json`）

| | 返回的店 | 青岚两店 GMV |
|---|---|---|
| 修复前（master，无身份） | 12 家店全部返回 | 53,712.89 / 84,141.09（另外 10 家是别的品牌） |
| 修复后（网关登录 `qinglan_ops`） | **只有 4、5 号店** | 53,712.89 / 84,141.09，与正确答案一致 |

面试讲法：模型写的 SQL 是 `select shop_id, sum(total_amount+freight_amount) from trd_order where … group by shop_id`，**没有任何店铺条件**，是执行层替它加上的，所以就算模型被注入了"忽略权限"，结果也一样。

## B2 收入口径：经销、代运营、品牌管理

**业务场景**：经销模式下货款是我方收入；代运营模式下货权在品牌方，我方只赚服务费。直接用实付金额当收入，代运营品牌会被高估十几倍。

**问题在哪**：`EvidenceRecallNode` 注入的证据。术语"我方收入"（`dataset/metadata/business_terms.yaml`）和【时间口径】（`TimeRangeHints.hints`）。

**是什么**：口径召回生效了，模型用对了 `revenue_amount`；但"3 月"被理解成 `settled_at` 在 3 月。3 月的账 4 月初才结算，所以取到的是 2 月业务月的账（数字和 2 月完全一致，已核对）。**术语只写了"算什么"，没写"按哪个时间算"**。

**方案对比**

| 方案 | 做法 | 问题 |
|---|---|---|
| A. 只改术语 | 在"我方收入"里加一句"按 `month_key`" | 只在召回到这条术语时生效；"服务费""结算金额"等其他按月记账的指标还会错 |
| B. 只改【时间口径】 | 问题里有"X 年 X 月"时，确定性地追加"按月记账的表用 `month_key = 'YYYY-MM'`" | 对所有有 `month_key` 的表（结算、目标、预算）都生效；不依赖召回 |
| C. 语义层 / 指标平台 | 预先定义指标，模型只选指标 | 最准，但要先把所有指标建模，成本高 |

**选择**：A + B 都做，成本都很低。B 是主力，因为它和第 7 步修 `2026-02-29` 是同一种"确定性提示"，已有实测证明有效；A 让收入类问题双保险。C 是长期方向，面试时可以说"如果指标再多，会往语义层走"。

**修复前后**（`B2.json` → `B2.after.json`）

| 品牌 | 模式 | 修复前（`settled_at` 在 3 月） | 修复后（`month_key='2026-03'`） | 正确答案 |
|---|---|---|---|---|
| 曜石 | 代运营 | 27,574.10 | **40,358.83** | 40,358.83 |
| 星屿 | 经销 | 243,826.37 | **342,502.64** | 342,502.64 |
| 青岚 | 代运营 | 7,685.81 | **10,792.31** | 10,792.31 |

其余 5 个品牌也全部一致（如果用实付金额当收入，曜石会是 663,415.85，高估 16 倍）。

## B3 多平台状态码异构

**业务场景**：天猫的"已完成"是 `TRADE_FINISHED`，京东是 `FINISHED_L`，抖音是 `5`。数仓统一层有 `order_status`，原始字段也保留着。

**结果**：修复前后都正确（天猫 597、京东 359、抖音 329、自营 117）。如果按 `platform_status='TRADE_FINISHED'` 过滤，其他三个平台 805 单全丢。

**为什么本来就对**：术语"平台订单状态"写明跨平台用统一状态；枚举值通道把 `TRADE_FINISHED`、`5` 和列对上（01）。枚举值是字面量，要精确匹配，不适合向量化；保留原始字段是因为对账时运营确实要按平台原始状态查。

## B4 表多且相似：漏召桥接表后同一条错 SQL 重写 10 次

**业务场景**：问"10 月 15 日华东区域仓数码家电可用库存"，要用日快照表（不是实时表），并且按一级类目过滤要走 SKU → SPU → 三级类目 → 二级 → 一级。

**问题在哪**
- `SchemaRecallNode` / `TableRelationNode`：召回和精选后的 schema 里没有 `prd_spu`。
- `SqlExecuteNode` 的异常分支：报错被 `SqlErrorClassifier` 正确判为 `TABLE_SELECTION`，但只把报错文本交回模型。
- `SqlGenerateNode`：重写时用的 schema 还是 `TABLE_RELATION_OUTPUT`，里面没有 `prd_spu`，所以模型只能继续猜 `prd_sku.category_id`。

**是什么**：**错误分类说对了，但没有闭环**。"选表错"的修复手段应该是"补表"，而系统给的修复手段只有"重写"。另外，同一条 SQL 连续出现说明重试已经无效，系统却不知道。

**方案对比**

| 方案 | 做法 | 问题 |
|---|---|---|
| A. 召回时多给几张表（topK 调大） | 一开始就多召回 | 每个问题的 prompt 都变长，选表噪声变大；01 里实测过 topK 和 Recall@5 的权衡 |
| B. 选表错误时回到 `SchemaRecallNode` 重新召回 | 整个召回重跑 | 问题文本没变，重跑大概率召回同样的表 |
| C. 选表错误时沿外键补邻居表（**选这个**） | 用失败 SQL 里的表做种子，查逻辑外键，把邻居表的 schema 并进 `TABLE_RELATION_OUTPUT`，每步最多 2 次（第 2 次能多走一跳） | 补进来的表可能不相关（B4 里补了 6 张，只有 1 张有用），但只在出错后发生，不影响正常问题 |
| D. 让模型自己说"缺哪张表"（上游的 `SQL_GENERATE_SCHEMA_MISSING_ADVICE`） | 模型生成补表建议，再精选 | 模型本来就不知道 `prd_spu` 存在，建议质量取决于它猜得对不对 |

**选择**：C。理由：报错里已经有确定的线索（失败 SQL 用了哪些表、哪个字段不存在），外键图是确定的，不需要再问模型；只在出错时触发，正常问题零成本。同时加"同一条失败 SQL 重复出现"的检测（`SQL_REPEAT_COUNT`），在多步计划里直接回到规划器（见 B6）。

代码：`service/schema/recall/SchemaExpansionService.expand()`（邻居按"连到几个种子表"排序，最多 6 张，过滤无权限的表）；`SqlExecuteNode` 异常分支里 `TABLE_SELECTION` 时调用；单测 `SchemaExpansionServiceTest`（第一跳补到 `prd_spu`，第二跳补到 `prd_category`）。

**修复前后**

| | SQL 生成次数 | 发生了什么 | 结果 |
|---|---|---|---|
| 修复前（`B4.json`） | 10 | 10 次都是 `Unknown column 'prd_sku.category_id'` | 无结果 |
| 修复后第 1 轮（`B4.after-r1.json`） | 3 | 第 1 次报错后补表 `prd_spu, …`，第 2 次就改成 `sku → spu`，不再报错 | 空（NULL） |
| 修复后第 2 轮（`B4.after-r2.json`） | 4 | 同上；之后语义校验驳回 2 次（一次是模型把 `prd_spu` 别名写成 `sku`，校验抓得对） | 空（NULL） |
| 正确答案 | | | 23 件（实时表会给 1,642） |

**还没解决的**：两轮都卡在**类目层级**：`spu.category_id` 指向三级类目，模型直接拿它和"数码家电"（一级类目）比，结果为空。术语"类目"里已经补了"要两次向上关联"，第 2 轮仍没照做。这是第 4 步里就记录过的口径问题，确定性的修法是：值召回识别到"数码家电"是 `prd_category` 里 `level=1` 的值时，在证据里直接给出三级类目 id 列表（`WHERE spu.category_id IN (…)`），不让模型自己走树。

面试讲法：这个例子正好能讲"修复要分层"：死循环是流程问题，补表解决了；剩下的是口径问题，要用确定性规则解决，不能指望重试。

## B5 大促时间窗：预售定金和尾款

**业务场景**：双11 预售，10 月 20–30 日付定金，10 月 31 日 20:00 起付尾款。大促 GMV 按尾款时间归属；`trd_order.paid_at` 记的是定金时间，直接用会漏掉全部预售单。

**问题在哪**：`SemanticConsistencyNode`（LLM 判断 SQL 是否回答了问题）+ `SemanticConsistenceDispatcher`（不通过就回 `SqlGenerateNode`，只受全局 10 次上限约束）。

**是什么**：口径已经对了（第一条 SQL 就用了 `balance_paid_at`），但 **LLM 校验没有上限、不稳定**：10 次里 9 次驳回，理由前后矛盾，有一次还要求加一个它自己编的"2025 自然年"条件。它有否决权，却没有被约束。

**方案对比**

| 方案 | 做法 | 问题 |
|---|---|---|
| A. 去掉语义校验 | 只靠 SQL 守卫和数据库执行 | 校验有时是对的（B6 里它抓到了 `shop_id = order_id` 的错误关联），全去掉会放过真错误 |
| B. 只让它查结构问题 | 改提示词，只查"多余的表、无条件关联" | 提示词约束不了 LLM 的输出，编造约束的问题还会有 |
| C. 投票 / 多次采样 | 校验 3 次取多数 | 成本 ×3，延迟 ×3；不稳定的判官投票还是不稳定 |
| D. 有界否决权（**选这个**） | 每个 SQL 步骤最多驳回 2 次（`gbi.nl2sql.max-semantic-rejects`）。多步计划里，第 2 次驳回先**回到规划器重写这一步**（同 B6）；问数模式或重规划次数已用完时才放行，交给 SQL 守卫和数据库做确定性校验 | 放行后可能执行一条真有问题的 SQL（见下） |

**选择**：D。理由：语义校验的价值在"前一两次"（抓多余的表、错误关联），之后的驳回大多是噪声；连续驳回本身就是一个信号："这一步的指令可能做不到"，比继续重写更该回到规划。

**一个设计上的修正（面试很好讲）**：第一版是"驳回 2 次就放行"。B6 第 1 轮里，第 3 步第 1 次驳回指出 `trd_daily_shop_sales.shop_id = trd_refund.order_id` 是错误关联，**这条驳回是对的**；放行后这条错 SQL 执行了，缺货退款数算成 0，报告的归因就错了。所以改成"多步计划里先回规划器，规划预算用完才放行"。

**修复前后**

| | SQL 次数 | 时间归属（尾款） | 金额口径 | 曜石结果 | 正确答案 956,004.20 |
|---|---|---|---|---|---|
| 修复前（`B5.json`） | 10 | 对 | — | 无结果（9 次驳回） | ✗ |
| 修复后第 1 轮（`B5.after-r1.json`） | 1 | 对 | 实付（`pay_amount`），不是 GMV | 873,706.96 | ✗ 少 8.6% |
| 补术语后第 2 轮（`B5.after-r2.json`） | 3 | 对 | 对 | 空表：模型多关联了"2025双11"活动表；校验驳回 2 次，第 2 次建议把预售表改成 INNER JOIN，放行后执行结果为空 | ✗ |
| 第 3 轮（`B5.after-r3.json`） | 2 | 对 | 对 | 943,238.18（多加了 `order_status IN (PAID, SHIPPED, COMPLETED)`） | ✗ 少 1.3% |

第 1 轮暴露了"大促GMV"术语写的"金额计全款"有歧义，模型理解成定金加尾款（等于实付）；已改成"金额同 GMV：`total_amount + freight_amount`"。

**结论**：卡死的问题解决了（10 次无结果 → 1~3 次有结果），预售归属 3/3 都对；但模型会**自己加条件**（活动、状态），而且校验的修改建议本身也会出错。这类错误执行不会报错，只能靠确定性的结果校验（99 第 3 条：比对 SQL 的过滤条件和问题里识别出的条件，多出来的条件要有依据）。

## B6 归因要多步：计划给了不可行的关联，校验又以计划为准

**业务场景**：品牌方最常问"为什么跌了"。数据里埋了根因：2026-10-12～18 华东区域仓数码家电缺货，缺货关单和退款激增。

**问题在哪**
- `PlannerNode` 生成了第 3 步"`trd_refund` 关联 `trd_daily_shop_sales` 统计缺货退款"，两张表之间没有关联路径。
- `SemanticConsistencyNode` 以计划为准：按正确路径（经 `trd_order`）写，驳回"不符合计划"；按计划写，驳回"关联错误"。
- `SqlGenerateNode` 超过 10 次时输出 `END`，`SqlGenerateDispatcher` 直接结束整张图：前两步已经算好的结果也没用上，没有报告。

**是什么**：**错误发生在规划层，修复只在 SQL 层**。SQL 层重试改不了计划；图里虽然有"计划修复"的环（`PlanExecutorNode` 校验失败 → `PlannerNode`，`PLAN_REPAIR_COUNT`），但只检查计划的 JSON 结构，SQL 执行失败从来不会回到规划器。这是第 8 步 R05 在 v2 数据上的复现。

**方案对比**

| 方案 | 做法 | 问题 |
|---|---|---|
| A. 调大重试次数 | 10 → 20 | 计划不变，重试再多也是锁死 |
| B. 失败步骤跳过，继续后面的步骤 | 第 3 步失败就跳过 | 报告少一块证据，而且缺的恰好是根因 |
| C. 开人工审核，让人改计划 | 03 的 HITL | 有效，但离线批量和接口调用时没人审 |
| D. SQL 步骤卡住时回到规划器重写这一步（**选这个**） | 满足任一条件：同一步失败 4 次（`replan-after-sql-failures`）、同一条失败 SQL 连续出现、语义校验连续驳回 2 次 → 输出 `__SQL_REPLAN__`，带上失败原因写进 `PLAN_VALIDATION_ERROR`，路由到 `PlannerNode`；要求"保留已完成的前 N-1 步、只改第 N 步及之后"；当前步骤号不变，已有结果保留；每个问题最多 1 次（`max-sql-replans`），用完退回原来的行为 | 规划器可能不听话，改了前面的步骤；重规划一次多一次 LLM 调用（约 20~40 s） |

**选择**：D。理由：复用图里已有的"规划器读 `PLAN_VALIDATION_ERROR` 重写"的能力（人工驳回也走这条路），只加了一条边 `SQL_GENERATE_NODE → PLANNER_NODE` 和一个触发条件；有上限，不会无限循环；问数（nl2sql-only）模式下计划是固定的一步，不触发。顺带修了两个上游问题：`PLAN_VALIDATION_ERROR` 在新问题开始时不清空（下一个问题的规划器会看到上一个问题的反馈）；规划器提示词写死成"用户驳回了计划"，现在改成"审核人或执行反馈"。

代码：`SqlGenerateNode.replanIfStuck()`、`SqlGenerateDispatcher`、`DataAgentConfiguration`（新边和新状态 `SQL_REPLAN_COUNT / SQL_REPEAT_COUNT / SEMANTIC_REJECT_COUNT / SQL_SCHEMA_EXPANDED`）、`GraphServiceImpl`（新问题清零）、`PlannerNode`。

## B7 数据时效：投放数据 T+1

**业务场景**：投放花费和流量来自平台后台的日报，T+1 才回传。运营早上问"今天各渠道花了多少"，正确回答是"数据截至昨天"，不能给一张空表让人以为没花钱。

**问题在哪**：`SqlExecuteNode` 执行成功、结果为空时直接返回空表；问数模式下没有任何生成解释的环节。术语"数据时效"已经在知识库里，但模型写 SQL 时用不上它。

**是什么**：系统没有"数据新鲜度"的概念。空结果有两种完全不同的含义："确实是 0"和"数据还没到"，系统分不出来。

**方案对比**

| 方案 | 做法 | 问题 |
|---|---|---|
| A. 靠术语让模型自己说明 | 已有"数据时效"术语 | 实测没生效；问数模式不生成文字 |
| B. 在 SQL 生成前拦截 | 识别"今天"+ T+1 表就提示 | 问题文本里的"今天"不一定落在 T+1 表上，误判多 |
| C. 执行后确定性解释（**选这个**） | 结果为空、且 SQL 涉及配置里的 T+1 表（`gbi.nl2sql.freshness-columns`）时，查该表 `MAX(stat_date)`（缓存 5 分钟）；SQL 里最晚的日期字面量（半开区间 `< X` 按 X-1 算）超过最新日期，就在结果里写明 | 只覆盖配置里的表；日期字面量是用正则取的，函数算出来的日期（`CURDATE()`）认不出来 |
| D. 元数据平台登记每张表的更新频率和最新分区 | 数仓调度回写 | 最准，但要接调度系统 |

**选择**：C。理由：只在"结果为空"时触发，正常查询零成本；判断是确定性的（查一次 `MAX`），不靠模型；说明写进结果的 `note` 字段，问数接口和报告都能看到。D 是生产环境的做法，面试时可以说"真实环境会从调度系统拿分区信息，原理一样"。

代码：`service/sql/freshness/DataFreshnessService.explainEmpty()`、`ResultSetBO.note`、`SqlExecuteNode` 成功分支；单测 `DataFreshnessServiceTest`。

**修复前后**（`B7.json` → `B7.after.json`）

| | 结果 | 说明 |
|---|---|---|
| 修复前 | 空表 | 无 |
| 修复后 | 空表 | "数据时效提示：查询结果为空，不代表实际为 0。mkt_ad_spend 最新数据日期 2026-10-30（T+1 回传，当天数据次日才有），查询的日期超出了已有数据的范围。" |
