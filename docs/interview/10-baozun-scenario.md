# 10 落到宝尊：七个业务难点、真实运行结果、现有方案和缺口

> **先说清楚边界**：原型参照品牌电商服务商（以宝尊电商为例）的公开业务模式。品牌名（曜石、青岚……）、店铺和所有数据都是**虚构的模拟数据**，不代表任何公司的经营数据。面试说法："我参照品牌电商代运营公司的公开业务模式，模拟了一套数仓，在上面做问数 agent。"业务和数据背景见 [00 第 0 节](00-architecture.md)。
>
> 数据改动见 `dataset/README.md` 的 v2 一节。例子在 `eval/baozun/examples.jsonl`，运行脚本是 `eval/baozun/run_examples.py`，原始记录（SSE trace + 结果）在 `results/baozun/`。
>
> 运行条件：2026-11-21，master 代码 + v2 数据，模型 qwen-plus，每个例子跑 **1 次**。单次运行有随机性（之前同一配置跑两次，23 题里有 6 题结果翻转），所以下面每个例子说明的是"这类问题会怎么出错"，不是稳定的准确率。

## B1 品牌数据隔离

**业务场景**：一个运营只服务青岚一个品牌。品牌之间是竞争对手，青岚的运营绝不能看到曜石的数据。这是服务商的合同义务，不是"最好有"。

**例子**（`results/baozun/B1.json`）
- 问题："2026年3月各店铺的GMV分别是多少？"
- 系统写的 SQL：`select shop_id, sum(gmv) from trd_daily_shop_sales where stat_date >= '2026-03-01' and stat_date < '2026-04-01' group by shop_id`
- 结果：12 家店全部返回。青岚两家店的数字是对的（天猫 53,712.89，抖音 84,141.09，和正确答案一致），但另外 10 家是别的品牌的数据。
- 根因：master 上没有登录态，也没有数据权限。SQL 本身没有错，错的是"谁在问"。

**方案（在鉴权分支 `claude/project-thread-alilb6`，见 09）**
- 网关解析身份 → 登录时把"能看哪些店"算好 → 执行前用 JSqlParser 把每一处 `trd_order`、`trd_daily_shop_sales` 原地替换成 `(SELECT * FROM … WHERE shop_id IN (4, 5))`。
- 按品牌隔离只需要把 `gbi_dept_data` 的映射从"部门 → 大区的店"换成"部门 → 品牌的店"（青岚 = 店 4、5），改写逻辑不变。

**为什么这么选**：见 09 第 4 节。核心理由是 SQL 是模型现写的，不能靠模型自觉加 WHERE（一次注入就绕过），也不能往 WHERE 里追加条件（LEFT JOIN 会变内连接）；派生表替换和外层写法无关。

**缺口和建议**
- 分支没合并，所以 master 上这个例子是"泄露"的。**合并分支**是第一优先级（99 第 2 条）。
- 按品牌隔离没有在 v2 数据上实测。补法：在 `ruoyi/sql/gbi_system.sql` 加一个"青岚运营"用户和部门映射，跑 `eval/data_permission/run_permission_eval.py`。

## B2 收入口径：经销、代运营、品牌管理

**业务场景**：同样是"收入"，经销模式下货是我们买断的，货款就是收入；代运营模式下货权在品牌方，我们只赚服务费。直接用 GMV 或实付金额当收入，代运营品牌会被高估十几倍。

**例子**（`results/baozun/B2.json`）
- 问题："2026年3月我们公司在各个品牌上的收入分别是多少？"
- 系统写的 SQL：用了 `fin_settlement.revenue_amount`（口径对），但过滤条件是 `settled_at` 在 3 月。
- 结果 vs 正确答案：

| 品牌 | 模式 | 系统结果 | 正确（`month_key='2026-03'`） | 如果用实付金额当收入 |
|---|---|---|---|---|
| 曜石 | 代运营 | 27,574.10 | **40,358.83** | 663,415.85（高估 16 倍） |
| 星屿 | 经销 | 243,826.37 | **342,502.64** | 372,285.48 |
| 青岚 | 代运营 | 7,685.81 | **10,792.31** | 131,372.28 |

- 系统结果和数据库核对过，正好是 **2 月业务月**的收入（2 月的账在 3 月 10 日结算）。
- 根因：口径召回生效了，"我方收入"这条术语把模型引到了 `revenue_amount`，"代运营只算服务费"这一层没错。新的错误在时间口径：财务里"3 月收入"指业务月，不是打款日。这一点没有写进术语。

**现在的方案**：业务术语"我方收入"（`business_terms.yaml`）写明按合作模式区分，通过口径通道召回（01）。实测确实把模型从 `pay_amount` 拉到了 `revenue_amount`。

**为什么这么选**：口径是业务定义，模型从表注释里学不到；做成术语库可以单独维护、单独召回，比改提示词更可控。备选是语义层（指标平台，先定义指标再让模型只选指标），更准，但要先把所有指标建模，成本高。

**缺口和建议**：在"我方收入"和【时间口径】里补一句"财务类问题的月份按 `month_key`（业务月），不是 `settled_at`"。这和第 7 步时间口径是同一种确定性提示，成本很低。

## B3 多平台状态码异构

**业务场景**：天猫的"已完成"是 `TRADE_FINISHED`，京东是 `FINISHED_L`，抖音是数字 `5`。数仓的统一层（DWD）有统一状态 `order_status`，但原始字段也保留着。模型如果按某个平台的原始码过滤，其他平台就全漏了。

**例子**（`results/baozun/B3.json`）
- 问题："2026年3月各平台已完成的订单分别有多少单？"
- 系统写的 SQL：`order_status = 'COMPLETED'`，按平台分组。
- 结果：天猫 597、京东 359、抖音 329、自营商城 117，**和正确答案一致**。
- 对照：如果按 `platform_status = 'TRADE_FINISHED'` 过滤，只剩天猫 597，其他三个平台 805 单全部丢失（这条 SQL 是手写的，用来说明影响有多大）。
- 一个小瑕疵：系统按 `created_at`（下单时间）而不是默认的 `paid_at` 归属月份，这次数字恰好一样，因为支付都在下单后几十分钟内；跨月下单的订单会不一致。

**现在的方案**：术语"平台订单状态"写明跨平台用统一状态；枚举值通道把 `TRADE_FINISHED`、`5` 这类取值和列对上（01）。

**为什么这么选**：枚举值是字面量，要精确匹配，不适合向量化（向量会把"华东"和"华南"拉得很近）。备选是让数仓把原始字段从模型可见的 schema 里去掉，最干净，但运营有时就是要按平台原始状态查（比如对账），所以保留字段、用术语约束。

## B4 表多且相似：实时库存 vs 日快照

**业务场景**：仓储有实时库存表和每日快照表，问历史某一天必须用快照。服务商的数仓里这种"同一实体、不同粒度或时点"的表非常多，选错表 SQL 照样能跑，只是数字错。

**例子**（`results/baozun/B4.json`）
- 问题："2026年10月15日华东区域仓数码家电的可用库存一共多少件？"
- 召回到的表：`dim_region, wms_warehouse, trd_order_address, wms_inventory, wms_inventory_snapshot, …`。**两张库存表都召回了，模型选对了快照表。**
- 但召回里没有 `prd_spu` 和 `prd_category`（按"数码家电"过滤要走 SKU → SPU → 三级类目 → 一级类目）。模型猜了一个不存在的字段 `prd_sku.category_id`，报错被正确归为"选表"类，然后**同一条错 SQL 重写了 10 次**，没有结果。
- 正确答案：23 件（这一周正好是埋的缺货周）；如果用实时库存表会得到 1,642 件。

**根因**：召回漏了桥接表。错误分类说对了"是选表问题"，但重写节点只能看到已经召回的表，看不到 `prd_spu`，所以怎么改都改不对。

**现在的方案**：多路召回 + 关联表通道补一跳外键邻居（01）；错误分类把原因交回模型（04）。这次两者都起作用了，但没有闭环。

**缺口和建议**（值得做，面试也很好讲）：**选表类错误回退到召回**。当 `SqlErrorClassifier` 判为"选表"且报错里有不存在的表或字段时，用报错里的表名（`prd_sku`）做种子，沿逻辑外键补召回（`prd_spu`、`prd_category`），再重写。另外，同一条 SQL 连续出现两次就应该提前停，而不是耗满 10 次。

## B5 大促时间窗：预售定金和尾款

**业务场景**：双11 预售，用户 10 月 20–30 日付定金，10 月 31 日 20:00 起付尾款。平台和品牌方的大促 GMV 按尾款支付时间归属。订单表的 `paid_at` 记的是定金时间，直接按 `paid_at` 过滤会漏掉全部预售单；尾款在 0 点后付的还会跨到下一天。

**例子**（`results/baozun/B5.json`）
- 问题："2025年双11期间（10月31日到11月11日）各品牌的GMV是多少？"
- 正确答案和按 `paid_at` 的写法对比（都用 MySQL 算出来）：

| 品牌 | 正确（预售单按尾款时间） | 按 `paid_at`（漏预售） | 少算 |
|---|---|---|---|
| 曜石 | 956,004.20 | 852,227.60 | 10.9% |
| 星屿 | 598,290.23 | 543,172.32 | 9.2% |
| 朵朵熊 | 153,830.32 | 133,506.66 | 13.2% |

- 系统的表现：**第一条 SQL 就用对了口径**，`is_presale=0` 按 `paid_at`、`is_presale=1` 按 `trd_presale_order.balance_paid_at`，这是"大促GMV"术语召回的作用。但同时出了三个问题：
  1. 多关联了一张 `mkt_activity`，而且没有关联条件（会把行数翻倍）。语义校验正确地抓住了这一点。
  2. 给维表加了不存在的 `is_deleted`，被 SQL 守卫拦下（`SQL守卫拦截[COLUMN/选表]：表 dim_shop 没有字段 is_deleted`）。
  3. **语义校验自己不稳定**：10 次里有 9 次不通过，理由前后矛盾，有一次还要求加一个"2025 自然年"的条件，这个条件是它自己编出来的。
- 结果：10 次用完，没有返回数字。

**根因**：口径层已经解决；卡在 LLM 语义校验，它的结论不稳定，又没有上限之外的出口。这和第 8 步 R05"计划与校验互相矛盾"是同一类问题。

**现在的方案**：术语"大促GMV"写明归属规则（v2 新增）；时间口径注入确定的日期区间（第 7 步）；JSqlParser 守卫拦住幻觉字段（04）。

**为什么这么选**：时间归属是确定性规则，放进证据比让模型推理可靠，P01 的 `2026-02-29` 就是反例。

**缺口和建议**
- 语义校验改成"有界"：同一类理由连续出现两次就放行，交给执行结果和报告溯源去兜底；或者只让它检查结构性问题（无条件的关联、多余的表），不检查口径（口径交给术语和规则）。
- step10 分支的 Turbo 模式本来就跳过语义校验、只靠守卫，可以拿这一题对比。

## B6 归因要多步：跨交易、仓储、退款

**业务场景**：品牌方最常问"为什么跌了"。原因可能是缺货（仓储）、发货慢（履约）、投放减少（营销）或者退货变多，单条 SQL 回答不了。数据里埋了一个根因：2026-10-12～18 华东区域仓数码家电缺货。

**例子**（`results/baozun/B6.json`，完整流程，关闭人工审核）
- 问题："曜石品牌在华东的销售额，2026年10月12日到18日这一周比前一周下降了多少？分析一下原因。"
- 计划（10 步）：两周销售额 → **两周缺货退款** → 两周大促情况 → … → Python 计算环比 → 报告。计划**主动把缺货列成了待验证的原因**，这是口径和术语召回带来的。
- 执行：
  - 第 1、2 步正确：本周 139,082.30，上周 172,718.25（用的是日汇总表的实付金额）。
  - 第 3 步（缺货退款）的计划写着"`trd_refund` 关联 `trd_daily_shop_sales`"，这两张表之间没有关联路径。模型写出经 `trd_order` 关联的正确写法，语义校验以"不符合计划"为由驳回；按计划写，又被以"关联错误"驳回。10 次用完，**流程结束，没有报告**。
- 正确答案的另一个角度：按订单表、排除缺货关单后，本周只有 62,444.73，比上周少 64%；日汇总表的实付是 139,082（少 19%），因为它把"付了钱又因缺货关单"的订单也算进去了。这本身就是缺货的信号，也是一个口径陷阱。

**根因**：计划阶段给出了不可行的关联路径，执行阶段的校验又以计划为准，两层互相锁死。这是第 8 步 R05 在新数据上的**复现**，说明它是系统性问题，不是偶发。

**现在的方案**：Planner 多步计划 + 人工审核（03，可以在执行前把这一步改掉）+ Python 降级（05）+ 报告的状态和原因（06）。

**缺口和建议**（最值得做的一条）
- **SQL 步骤失败时回退到规划器重写这一步**，而不是在 SQL 层耗满 10 次。图里已经有"计划修复"的环（`PLAN_REPAIR_COUNT`），可以复用。
- 语义校验在多步场景下只校验"SQL 是否回答了这一步的问题"，不校验"是否照抄了计划里的关联路径"。
- 面试时可以讲：开启人工审核时，审核人看到第 3 步写着"`trd_refund` 关联日汇总表"，可以直接改成经 `trd_order` 关联，这正是 HITL 修改计划的价值。

## B7 数据时效：投放数据 T+1

**业务场景**：订单接近实时，但投放花费和流量来自平台后台的日报，T+1 才回传。运营早上问"今天的 ROI"，正确回答是"投放数据截至昨天"，不能给 0，更不能编。

**例子**（`results/baozun/B7.json`）
- 问题："今天（2026年10月31日）各投放渠道的花费分别是多少？"
- 系统：SQL 正确，过滤 10 月 31 日，**返回空结果，没有任何说明**。数据库里投放数据最新到 10 月 30 日。
- 根因：没有"数据新鲜度"的概念。空结果在报告接口里会被标成 DEGRADED（06），但在问数接口里就是一张空表，用户会以为"今天没花钱"。

**现在的方案**：**没有**。术语"数据时效"已经写进知识库（v2 新增），但这次没有生效：问数模式下没有生成解释的环节。

**缺口和建议**：在表的元数据里加"更新频率"和"最新分区"（运行时查一次每张表的 `MAX(stat_date)`，缓存起来）。SQL 执行返回空、且查询的时间超过该表的最新日期时，确定性地回复"该表数据为 T+1，最新到 X 日"。成本低，而且是品牌方日常最常遇到的问题之一。

## 面试时怎么用这一页

1. 先讲 00 第 0 节：数据从哪来、长什么样，推出 agent 为什么这么设计。
2. 再挑 2~3 个例子讲"问题 → 系统怎么错 → 根因 → 方案或下一步"。推荐 B2（口径召回确实起作用，又暴露了新问题）、B5（预售口径）和 B6（计划与校验锁死，两份数据上都复现了）。
3. 被问"准确率多少"时，说清楚这是单次运行的个例，规模化数字见 07 和 99。
