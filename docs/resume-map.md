# 简历逐条对照

简历是模板，里面的数字不算数，这里只讲**做了什么**。每一条按同样的格式回答：

- 做了什么（代码在哪）
- 为什么这么做，考虑过哪些方案
- 解决什么问题
- 实测指标，从多少到多少
- 哪些说法要收着讲

细节都在 `docs/design/stepN-*.md` 的“面试问答”一节。

---

## 1. Schema 召回：元数据、业务术语、列样本、多轮、枚举值，180 题 Recall@5

- **做了什么**：`SchemaRecallNode` 改成 7 路召回，用 RRF 融合（只看名次，不调权重）后取前 K：
  - 表向量、列向量
  - BM25 关键词
  - 口径：术语表里写明了用哪些表
  - 枚举值：数据库 DISTINCT，比如“华东”指向 `dim_region.big_region`
  - 关联表：沿逻辑外键补全 JOIN 路径
  - 多轮：带上前几轮的问题

  向量存 Milvus，重启不用重新向量化。代码在 `service/schema/recall/`，评测在 `eval/table_select/`。
- **为什么**：
  - 上游的召回**根本不看问题**，这是最大的问题。
  - 只用向量，遇到“华东”“GMV”这类字面值和口径时不准。
  - 直接让 LLM 选表：86 张表的 M-Schema 约 2 万 token，又贵结果又不可复现。
  - 枚举值没有向量化，因为向量会把“华东”和“华南”拉得很近。
- **指标**（180 题，Recall@5）：
  - 上游 5.6% → 修复“不看问题”后 69.8% → 全通道 86.2%。
  - 注释消融版 82.0%；Milvus 复测 87.9% / 79.8%。
  - 贡献最大的是口径（+5.6）和列向量（+5.1）。
  - embedding 在注释缺失时值 7.8 个点：没有它，缺注释那批题从 66.7% 掉到 34.7%。
- **要收着讲**：
  - 目标 93.3% 没达到。
  - 召回通道是看过错题以后设计的，所以 180 题算不上干净的 holdout。
  - 生产环境的 `SchemaRecallNode` 没有传多轮上下文，按生产等价的配置算是 84.5%。

## 2. 6 类 StateGraph 节点：意图、召回、规划、SQL、Python、报告

- **做了什么**：图是上游的 Spring AI Alibaba Graph，实际有十几个节点：意图 → 证据 → 改写 → Schema 召回 → 表关系 → 可行性评估 → 规划 → SQL 生成 → 语义校验 → 执行 → Python 生成/执行/分析 → 报告。简历里的“6 类”是按职能归的。
- **怎么讲**：连线和状态字段是从上游借的，我改的是节点内部和失败路径：
  - 召回（第 3 步）
  - 执行前守卫和带原因重写（第 4 步）
  - 规划后的人工审核（第 5 步）
  - Python 降级（第 6 步）
  - 时间口径（第 7 步）
  - 报告组装（第 8 步）
- **要收着讲**：不要说图是自己从零搭的。可以说：在上游的图上做了召回、守卫、审核、沙箱和报告五处改造，每一处都有前后对比。

## 3. 人工审核：计划展示、修改、驳回，threadId 恢复，最多 3 次重规划

- **做了什么**：
  - 用 `interruptBefore` 在人工审核节点前暂停。
  - 审核人可以确认、直接改计划 JSON，或者驳回并写原因。
  - 驳回意见会累积；重新规划的上限 `gbi.hitl.max-replans=3`，超过就结束本轮。
  - 检查点可以存 MySQL（`MysqlSaver`），重启后用同一个 threadId 继续执行。

  代码在 `service/hitl/`。
- **为什么**：
  - 在节点里阻塞等待会占住线程和连接，所以用暂停加检查点。
  - 修改直接改 JSON，不再过一遍 LLM，可预期也可审计。
  - 检查点选 MySQL，因为元数据库本来就有，审核记录又是审计数据。Redis 要多一个依赖；文件存储在多实例下不共享。
  - 上限是 3：驳回 3 次还不满意，通常是问题没说清楚，继续让模型猜只是烧钱。
- **指标**：9 个单测，加上真实后端的端到端记录。上游内存检查点下，重启后确认没有任何输出，因为状态丢了；改成 MySQL 后能完整执行到报告，耗时 132.7 秒。
- **要收着讲**：没有对“审核让结果变好了多少”做量化，这里只证明了功能和恢复能力。

## 4. SQL 生成和 4 项校验，失败重写，错误分类

- **做了什么**：
  - SQL 用 Qwen 生成（DashScope；Schema 的格式借鉴 XiYan-SQL 的 M-Schema）。
  - 执行前用 JSqlParser 守卫（`service/sql/guard/SqlGuard`）检查：语法、只读（禁止多语句和写操作 CTE）、表白名单（智能体选定的表）、字段是否存在。
  - 语义一致性沿用上游的 LLM 节点。
  - 被拦下或执行报错时，`SqlErrorClassifier` 按 SQLState 和厂商错误码分成**选表 / 方言 / 执行**三类，把原因交给模型重写。
  - 第 7 步加了时间口径（按日历算好半开区间）和非法日期的修复提示。
- **为什么**：
  - 正则挡不住 `SELECT 1; DROP …`，还会把 `updated_time` 误判成 update 语句。
  - Druid WallFilter 在连接池层面，拿不到智能体级别的白名单，也没法把原因结构化地交还给 LLM。
  - JSqlParser 能拿到语法树，RuoYi-Cloud-Plus 做行级权限也用它。
  - 解析失败一律拒绝；真正的安全边界是只读账号，守卫的价值在于“拦下并告诉模型为什么”。
- **指标**：
  - 75 条正反例全部一致（误拦 0/30，攻击拦截 28/28），平均每条 3 ms；错误分类 14/14。
  - 40 题配对样本：SQL 执行成功率 86.7% → 100%，首次即成功 76.7% → 90%，选表类错误 33 → 10 次。
  - 一个具体例子：P01 修复前连续 10 次写出 `2026-02-29`，修复后第 2 次就成功。
- **要收着讲**：
  - “结果按指标/维度/时间窗校验”只做到一部分：时间窗由时间口径保证，指标和维度靠 LLM 语义校验和口径证据。另外有确定性的检查：结果全空就降级，报告的数字要能溯源。但没有逐个指标的规则校验器。
  - 75 条用例和守卫是同一个人写的。
  - 没有部署 XiYan-SQL 模型。

## 5. Python 沙箱：Docker 容器池，1 CPU / 500 MiB / 60 s / 无网络，失败 5 次显式降级

- **做了什么**：
  - 修了上游容器池的配置：`NanoCPUs`、`MemorySwap = Memory`（不许用 swap）、`PidsLimit=64`。
  - 修了池化容器的输出泄漏：按启动时间截取日志。
  - 退出码 137 时区分是 OOM 还是超时。
  - 失败 5 次后由 `PythonExecuteNode` 和 `PythonAnalyzeNode` 显式降级：写明哪一步、重写了几次、最后是什么错误，并且不影响同一个会话里的下一题。
- **为什么**：
  - 上游的配置“看起来有限制，实际没生效”。
  - 一个任务读到别的任务的输出，是安全问题，也会让结论出错。
  - 选 Docker，而不是 gVisor / Firecracker：Docker 现成，资源限制够用；更强的隔离可以作为下一步。
- **指标**：CPU 1.99 → 1.00 核；内存上限 1000 → 500 MiB；进程数不限 → 64；跨任务泄漏 7/8 → 0/12；真实 Docker 用例 9/9。
- **要收着讲**：宿主机是 cgroup v1，v2 没有实测。

## 6. ECharts + Markdown 报告，经 OpenAPI 对外

- **做了什么**：
  - `POST /openapi/v1/reports`，用 springdoc 生成 OpenAPI 3 文档。返回计划、Markdown（末尾附**系统生成**的证据：实际执行的 SQL 和结果）、校验过的 ECharts JSON、状态和失败原因。
  - `NumberTrace`：报告里找不到出处的金额会列在 `untracedNumbers`。
  - `ResultTotals`：系统先算好合计，再交给报告节点引用。
- **为什么**：
  - 调用方不应该去解析几十种 SSE 消息。
  - 证据由系统附上，比在提示词里要求“请引用 SQL”可靠。
  - 不用 LLM 给报告打分：它看不出“数抄错了”。
- **指标**（8 题样本）：
  - 完成 3/8，完成的报告都有合法图表和证据。
  - R07 的 SQL 是对的，但报告把 -50% 写成了“+0.74%”，跑两次错两次；加了 `ResultTotals` 后变对。
  - R40 的 UV 也由错变对。
- **要收着讲**：样本很小；溯源检查有误报（单位换算、均值），也会漏报。

## 7. 320 题问数评测集：按域、表、时间切分，4 类任务，conversationId 串联计划、SQL 和修复

- **做了什么**：
  - 80 个题族 × 4 组参数，每题都有在 MySQL 上验证过的标准 SQL。
  - 任务类型：单表 96 / 多表 96 / 多轮 64 / 多步 64；意图 5 类，各 64 题。
  - dev 192 / holdout 128，按**题族 + 月份**切分。
  - 每题一个 threadId（conversationId），完整的 SSE 流存为 trace，可以还原“计划 → 每次 SQL → 守卫和错误分类 → 修复了几次”。

  代码在 `eval/nl2sql/`、`eval/scripts/run_nl2sql.py`。
- **为什么**：
  - 比较执行结果（EX），不比较 SQL 文本，因为同一个问题有多种正确写法。
  - 题族模板由人写，不让 LLM 批量出题，否则标准答案本身可能错。
  - 不用 Spider / BIRD，因为测不出这个场景的口径和跨域问题。
  - 按题族切分是为了防止 holdout 泄题。
- **指标**：40 题配对样本，两个后端用同一个模型并排跑：EX 50.0% → 56.7%，多表题 EX 20% → 40%。
- **要收着讲**：
  - 只跑了 40 题，holdout 没用过，目标 85% 差距大。
  - 剩下的错误里，最大一类是“拿一级类目名去过滤三级类目”，13 题里占 5 题。

## 8. 指标：SQL 执行成功率、多步完成率、报告耗时对比人工基线

| 指标 | 实测 | 口径 |
|---|---|---|
| SQL 执行成功率 | 86.7% → 100% | 30 道 SQL 题，最终有结果集返回 |

## 9. 数据源：MySQL / PostgreSQL / Hologres（ADB-PG），Turbo / Mix，云上 + 本地混合部署

- **做了什么**：数据集同时生成 MySQL 和 PostgreSQL 两份；守卫和错误分类在两种库上都实测过。Hologres 和 ADB-PG 走 PostgreSQL 方言，错误码也做了映射。
- **要收着讲**：
  - Hologres / ADB-PG 只能说“代码支持，没有在真实实例上验证”。
  - Turbo / Mix 和云上 + 本地混合部署**没有实现**。建议从简历上删掉，或者改成“了解 GBI 的 Turbo / Mix 设计”。

## 10. RuoYi 微服务、网关、登录鉴权、数据权限

- **做了什么**：参考 RuoYi-Cloud，在 gbi-agent 前面加了两个服务；数据权限参考 RuoYi-Cloud-Plus，按问数场景改了做法。代码在 `ruoyi/` 和 `gbi-agent/.../security/`，`scripts/up.sh` 设置 `SECURITY=on` 就能一键拉起。
  - **gbi-gateway**（Spring Cloud Gateway）：唯一入口，依次做五件事：
    - 删掉客户端带来的身份头
    - 验 JWT
    - 查 Redis 会话
    - 给身份头做 HMAC 签名后转发
    - 按用户限流
  - **gbi-auth**：BCrypt 密码，连续 5 次错误锁定 10 分钟；JWT 只是 Redis 会话的钥匙；登录时按 RuoYi 的 data_scope（1 全部 ~ 5 仅本人）算出这个人能看哪些店、哪些仓。
  - **gbi-agent**：
    - 只认网关签名，直连一律 401
    - 功能权限按路径配置，没配的默认要管理员
    - 校验 threadId 归属，防止接管别人的审核会话或读别人的报告
  - **表级权限**：召回后去掉无权限的表，执行前再按守卫解析出的表检查一次。
  - **行级权限**：用 JSqlParser 把每一处受控表换成 `(SELECT * FROM t WHERE shop_id IN (...)) 别名`。50 张受控表的策略由脚本根据外键生成，子表通过 IN 子查询追到父表。
- **为什么**：
  - 上游完全没有鉴权，连模型的 API Key 都能直接读到。
  - 问数的 SQL 是大模型现写的，没有 Mapper 可以加 `@DataScope` 注解，权限只能在执行前对 SQL 做确定性改写。
  - 没有像 RuoYi-Plus 那样往 WHERE 里追加条件，原因有两个：条件放进 LEFT JOIN 查询的 WHERE 会把外连接变成内连接；模型起的别名不可控，条件要跟着重新限定。
  - 没用数据库 RLS：MySQL 没有这个功能；PostgreSQL 的 RLS 要按用户建连接，连接池就没法共享了。
  - 比 RuoYi 多做了网关签名：不靠内网隔离，agent 能自己证明请求确实来自网关。
- **指标**（全部经过网关实测）：
  - 上游没有任何权限控制，以下每一项原本都会越权。
  - 276 条标准 SQL × 6 个用户：
    - 涉及未授权表的 **380/380 拦截**
    - 可执行的 **1,276/1,276** 和“物理隔离副本”（MySQL 视图，不经过改写）结果一致，其中 711 条的结果确实被过滤改变了
    - **误拦 0**
  - 28 条手写攻击 **0 泄露**；接口层 11 项全部通过（伪造身份头、篡改令牌、注销后的旧令牌、直连 agent、读别人的报告……）。
  - 网关开销：P50 **+0.98 ms**，P99 **+3.75 ms**。行级改写每条约 1.7 ms。一次问数要 77–98 秒，这些都可以忽略。
  - 真实模型端到端：同一个问题，admin 看到 12 家店，华东运营看到 5 家，店铺运营看到 7 家，每家店的数字和 admin 的完全一样。
  - 无权限的问题，从重试 10 次改为 2 次就停止并说明原因：86.8 秒 → 54.3 秒。
- **要收着讲**：
  - 只在 MySQL 上实测过。
  - 对比用的物理隔离副本和改写用的是同一份策略文件：它证明“改写正确地套用了策略”，不证明“策略定义得对”。
  - 没做列级脱敏。
  - 召回里的枚举值可能露出别的店铺名称（维表是共享的）。
  - 业务口径里出现的表名会让模型写出无权限的表，现在靠执行前检查拦下。
  - 没接 Nacos、Sentinel。
  - 详见 [设计文档](design/security-ruoyi-gateway-data-permission.md)。

## 最可能被追问的三件事

1. **“你的提升是怎么测的？”** 两个后端并排跑，同一道题、同一个模型；每个改动都有开关可以关掉。召回从 5.6% 到 86.2%，执行成功率从 86.7% 到 100%。
2. **“哪里没做好？”** 实话实说：
   - 召回没达到 93%。
   - EX 离 85% 很远，主要是口径错误。
   - 报告完成率 3/8：规划出的计划和语义校验互相矛盾，加上归因题召回不到根因所在的业务域。
   - 每一个都已经定位到原因，修复方向也写在设计文档里。
3. **“为什么样本这么小？”** 免费额度用完了，所以先跑配对样本证明方法和工具链；完整评测各需一条命令，支持断点续跑。
